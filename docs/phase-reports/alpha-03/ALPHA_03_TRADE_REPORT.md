- 日期：2026-11-28
- 切片：S5-C 玩家交易最小版
- ADR：`docs/ADR/ADR-050-face-to-face-player-trading.md`

## 1. 目标与产品价值

Alpha 0.3 的路线把“玩家间经济”列为核心玩法，但此前玩家只能和 NPC 商店
交易：打到的多余装备、材料与药水无法给队友或朋友，金币也只能回到商店。
本切片交付最基础的面对面交易，回答三个产品问题：

- **再玩 30 分钟**：打到重复装备后可以换回自己需要的材料或金币，战利品
  不再只有“卖店”一个出口。
- **明天回来**：交易让玩家之间的物品与金币流动，形成比单人刷怪更长的目标。
- **和别人一起玩**：交易是直接的多人协作行为，也是后续拍卖行/摆摊的基础。

## 2. 交付范围

1. **邀请与接受**：同图、3 格内、双方存活；邀请 30 秒过期；同一时间一人
   只能参与一笔交易。
2. **报价**：双方各可放入最多 8 个完整物品堆叠与 0–1,000,000 金币；只有
   背包物品可交易，新手武器等“无出售价”的绑定物品不可交易。
3. **双确认**：任何报价修改都会清除双方锁定；双方锁定后服务端自动结算。
4. **原子结算**：物品、金币在同一 PostgreSQL 事务内交换；钱包与
   `currency_ledger` 同事务；`asset_commands` 以 `tradeId` 幂等。
5. **生命周期**：取消、离开地图、过图、断线、死亡都会取消交易并通知双方。
6. **客户端**：附近玩家「交易」、邀请横幅、右侧停靠交易面板、背包整堆加入、
   金币输入、锁定/取消、完成/取消结果与背包即时刷新。
7. **隐私**：报价与交易状态只走私有消息，公开 Room State 不新增字段。

### 3.1 结算事务

1. 按角色 UUID 升序 `FOR UPDATE` 双方角色行，与既有资产命令使用同一把行锁，
   避免交叉交易死锁。
2. 双方分别写入 `asset_commands`（kind `trade_settle`，幂等键包含 `tradeId`）；
   任一方已存在时返回幂等结果。
3. 锁定并复核所有报价物品（归属、背包、数量、可交易）与双方钱包。
4. 先把所有“移动”物品停放到接收方的唯一负槽位，再删除被合并的堆叠并合并
   数量，最后写入正式槽位——交换双方槽位不会产生唯一索引冲突，物品实例 ID
   与掉落审计引用保持不变。
5. 同事务更新双方钱包并写入两条 `currency_ledger`；提交成功后才向客户端确认。

### 3.2 失败与取消

- 结算时背包满、金币不足、物品已被使用/出售、距离过远：事务整体回滚，交易
  回到 `open`，双方解锁并收到原因；服务端会剔除已不在背包中的报价物品。
- 结算时离开/过图/断线/死亡：交易关闭为 `cancelled`，另一方可立即开始新的
  互动。
- 重复提交同一笔交易：`tradeId` 幂等，不会二次移动资产。

## 5. 设计复盘

**正确的部分**

1. 交易会话留在 Room 内存，只有结算进入 PostgreSQL——避免了为短生命周期
   交互再建一套持久会话表与恢复语义。
2. 结算锁的是角色行而不是“交易行”，与拾取/商店/装备共用同一把串行锁；
   双角色按 UUID 排序，交叉交易不会死锁。
3. 槽位交换用“负槽位停车 → 合并/删除 → 落位”，既避免唯一索引冲突，又
   保留物品实例 ID 与掉落审计引用。
4. 客户端只表达“放入哪些物品、给多少金币”，数量、可交易性与最终结果全部
   由服务端从背包/钱包重新计算。

**不足与风险**

- 交易会话不跨进程/重启（TD-SRV-19）；服务端重启会取消进行中的交易，但已
  提交的结算不受影响。
- 只支持整堆交易，没有数量拆分；没有税率、交易历史查询、黑名单或防诈骗
  提示（TD-ECO-06）。
- 没有交易中的聊天与“对方正在输入”类反馈；交易面板与商店共用右侧停靠位，
  一次只能开一个。
- 未做真人长时间试玩与远端 CI；正式美术与八方向角色帧仍开放。
- 路线图 Alpha 0.3 要求“玩家交易 1,000 次压测无复制/丢失金币或物品”；本
  切片用真实 PostgreSQL 并发/幂等测试与 50 人容量 sanity 验证了单笔与重复
  结算，但 1,000 次连续交易的版本级经济压力测试仍未执行，列为版本门禁。
