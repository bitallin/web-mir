# Web Legend 产品愿景与长期演进原则

- 版本：1.0（2026-11-25，Alpha 0.1 完成后确立）
- 维护者：产品与架构负责人（Tech Lead / CTO / Game Director）
- 配套文档：`docs/PROJECT_ROADMAP.md`（版本路线）、`docs/ALPHA_03_EXECUTION_PLAN.md`
  （当前迭代）、`docs/EVOLUTION_LOG.md`（里程碑演进与复盘）、
  `docs/ENGINEERING_LEARNINGS.md`（工程经验）

## 1. 使命

打造一款浏览器即开即玩、服务端权威、可持续更新内容的传奇类 2D 多人在线
MMORPG。它不是技术演示，也不是功能堆砌的网页小游戏，而是一款玩家愿意每天
回来、能长期成长、能与他人协作和竞争的产品。

判断任何需求时先问三个问题：

1. 它是否让玩家更愿意再玩 30 分钟？
2. 它是否让玩家更愿意明天回来？
3. 它是否让玩家更愿意和别人一起玩？

三个都答“否”的功能，即使技术上正确，也不应优先做。

## 2. 核心体验循环

### 2.1 分钟级循环（0–3 分钟）

发现目标 → 接近 → 战斗 → 获得反馈（伤害、掉落、金币、经验）→ 立刻变强或
获得可预期的收益。

要求：操作不超过一次有效意图；反馈延迟低于一次往返；每次战斗都有可见收益。

### 2.2 会话级循环（30–60 分钟）

补给（药水/装备）→ 前往更危险的区域 → 击杀更高价值的怪物 → 带回战利品 →
出售/购买/装备 → 形成下一次外出的目标。

要求：金币必须有稳定消耗端；背包与商店必须让“回城”有意义；死亡必须有代价
但不劝退。

### 2.3 长期循环（天/周）

等级与装备追求 → 稀有掉落与 Boss → 组队、公会、交易、PK → 排行榜与荣誉 →
新内容与新目标。

要求：每个版本都必须回答“玩家下周为什么回来”。

## 3. 产品支柱

1. **即时可玩**：打开浏览器即可进入，不下载客户端，不注册复杂账号。
2. **手感优先**：自动攻击、移动预测、技能反馈、动画与音效构成打击感；手感
   不好时，系统再多也没有意义。
3. **职业差异**：战士抗、法师爆发、道士持续与辅助；差异必须被玩家“玩出来”，
   而不只是数值表不同。
4. **风险与回报**：越危险的地方收益越高；死亡有代价；补给与撤退是决策。
5. **多人价值**：看见别人、与他人合作、与他人竞争，是 MMORPG 与单机的分界。
6. **持续生产**：新怪物、物品、技能、地图尽量只改内容数据，不改核心代码。
7. **可信运营**：资产不重复、不丢失；所有运营动作可审计、可回滚。

## 4. 设计原则

- **服务端权威不可妥协**：位置、伤害、掉落、金币、经验、装备只能由服务端
  裁定；客户端只表达意图。
- **先完整体验，再扩展系统**：一个能玩通的纵向切片优于五个半成品系统。
- **内容驱动优先**：能用内容数据表达的，不写代码；必须写代码的，先定义 schema。
- **经济是产品的一部分**：任何产出都必须有消耗端；任何交易都必须走账本与事务。
- **不做过早抽象**：真实需求出现前，不引入微服务、消息队列、通用引擎或复杂
  框架；由指标触发演进。
- **占位资源必须可见地是占位**：在正式美术到位前，统一风格、明确标注，不把
  临时资源伪装成完成品。
- **删除内部术语**：玩家界面不出现“阶段 N”“MVP”“TD-xx”等研发词汇。

## 5. 体验质量标准

每个可玩切片必须同时通过以下检查，缺一不可：

| 维度   | 问题                                                 |
| ------ | ---------------------------------------------------- |
| 功能   | 目标行为是否真实可用，是否走真实服务端与数据库链路？ |
| 稳定   | 断线、重连、并发、重复操作是否安全？                 |
| 操作   | 完成目标需要几次操作？是否有无效点击与拒绝提示？     |
| 反馈   | 玩家能否在 100ms 内知道“我做到了什么”？              |
| 趣味   | 是否存在选择、风险或成长目标？                       |
| 多人   | 是否创造与他人协作/竞争的理由？                      |
| 视觉   | 是否符合统一设计语言，是否泄露内部实现？             |
| 可度量 | 是否有测试、指标或试玩证据证明它变好了？             |

## 6. 版本演进与门禁

版本路线以 `docs/PROJECT_ROADMAP.md` 为准；本文只固定原则：

- **Alpha 0.2**：核心体验。三职业差异、怪物威胁、死亡代价、经济闭环、正式
  美术第一版。
- **Alpha 0.3**：多人玩法。任务、Boss、组队、副本、社交、交易、PK、排行榜。
- **Beta**：内容生产与运营。表单化工作台、资源管线、活动、分析、客服与安全。
- **长期**：多区服、动态实例、大规模多人玩法，按指标触发。

每个版本必须满足：

1. CI verify、CI E2E、50 人容量、经济不变量、崩溃恢复全部通过。
2. P0/P1 债务清零；新增债务必须有编号、证据与处理版本。
3. 至少一个真实试玩切片，有截图/录制与试玩记录。
4. 版本报告写清“哪些设计正确、哪些不够好、下一次怎么做得更好”。

## 7. 决策边界

可自主决定：任务拆分、局部实现方案、小范围重构、测试补充、性能优化、文档
更新、内容数值微调。

必须先提方案：更换核心引擎/网络框架/数据库模型、破坏兼容性的协议调整、
核心架构大规模重构、引入新基础设施、长期产品方向调整、不可逆生产数据操作、
大规模经济与平衡规则调整。

## 8. 复盘节奏

- 每个可玩切片结束：更新 `docs/WORKLOG.md` 与 `docs/PROJECT_STATUS.md`，
  在 `docs/ENGINEERING_LEARNINGS.md` 记录可复用经验。
- 每个版本结束：阶段报告 + 试玩证据 + 债务复核 + 路线校准。
- 同类问题第二次出现时，必须把预防措施写入 `AGENTS.md` 或自动化门禁，而不是
  再次手工修复。

## 9. 成功度量（Alpha 阶段）

不以代码量或功能数量衡量进度，以下列信号为准：

- 新玩家 30 分钟内完成“创建→战斗→掉落→装备→商店→再成长”闭环。
- 三个职业在 10 级时的战斗方式可被玩家明确描述出差异。
- 玩家在没有外部指引时知道“下一步该做什么”。
- 金币产出与消耗大致平衡，2 小时内不出现无限膨胀。
- 50 人同图 10 分钟稳定，无资产重复/丢失。
- 每次版本迭代后，回归门禁与试玩证据完整可复现。
