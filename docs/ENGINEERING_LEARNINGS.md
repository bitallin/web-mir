# Web Legend 工程经验记录

- 目的：把真实项目中反复出现、代价高昂或验证有效的经验沉淀下来，避免同类问题
  第二次出现时重新踩坑。
- 规则：每条经验必须有实际案例或证据；只写“为什么”和“下次怎么做”，不写泛泛
  而谈的原则。需要所有 Agent 强制遵守的，才提炼进 `AGENTS.md`。
- 维护：由 Tech Lead 在里程碑/复盘时追加；不删除历史条目，过时可标注“已失效”。

## EL-001：独立端口不等于独立环境

- 案例：阶段 10 审计中，E2E 使用独立端口（5184/5185/3086/2587）但仍写开发库；
  开发栈的 Control API 与 E2E 的 Control API 共用 `outbox_events`，开发进程抢走
  kick 命令并投递给不含该会话的 87 端口，`applied=0` 仍标记成功，测试假失败。
- 经验：隔离必须覆盖**所有共享状态**——数据库、Outbox、内容激活、Redis、
  文件系统、端口。只换端口或只换进程不算隔离。
- 下次：新增测试栈时列出“它会写哪些共享状态”，逐项隔离；E2E 默认一次性数据库
  并在结束时删除（ADR-025）。

## EL-002：测试结果的“看起来通过”比失败更危险

- 案例：内容发布 E2E 里有 `expect(x).toBeDefined(); if (x === undefined) return;`
  的“空通过”分支；容量报告把 `LOAD_ATTACKERS` 误读成额外玩家，导致“30+10”
  被高估为 40 人。
- 经验：门禁必须断言“目标行为确实发生”，而不是“没有报错”。指标口径必须写进
  脚本输出，不能只存在于口头理解。
- 下次：每个 E2E 至少断言一个用户可见结果或数据库结果；压测脚本显式打印
  玩家/攻击者/时长/接受率/拒绝码，并断言接受率下限。

## EL-003：React updater 里做副作用会静默丢执行

- 案例：Alpha 0.1 的 Toast 去重标记写在 `setState(updater)` 内部，并依赖 updater
  里的 `setTimeout`；React 异步执行 updater，定时器从未安排，提示永不消失。
- 经验：状态更新函数必须是纯函数。去重、定时器、日志、网络请求都放在
  updater 之外，用同步读取的 ref 或先算后写。
- 下次：涉及定时消失的 UI，E2E 必须断言“出现后在 N 秒内消失”，而不是只断言
  出现。

## EL-004：内容 schema 加字段会改变历史 Release 的 checksum

- 案例：为商店给物品增加 `buyPrice/sellPrice` 时，若使用 Zod `.default(0)`，
  旧 Release 的 payload 在解析后被补上默认字段，canonical JSON 变化，checksum
  与库中记录不一致；`ContentStore` 会拒绝该 Release 并沿用旧快照。
- 经验：内容 schema 的演进要考虑**不可变历史数据**。可选字段用 `.optional()`，
  在代码里用 `?? 0` 解读；只有确认能重算/重发所有历史 Release 时才能用
  `.default()` 或改 `schemaVersion`。
- 下次：修改 `content-schema` 后，用一条真实历史 payload 做“解析→checksum”
  回归测试；新增字段的兼容策略写进 ADR。

## EL-005：运营可以直接制造登录事故

- 案例：内容发布删除一个仍被玩家持有的物品模板后，持有者加入世界时报
  “资产加载失败”，整个地图的未领取掉落也可能停止恢复（TD-DATA-04）。
- 经验：任何“可删除被引用的内容”都必须做引用完整性校验；加载路径必须逐条
  容错，不能一条坏数据拖垮整批。
- 下次：内容发布前查询 `item_instances` 的 distinct 模板；批量加载用
  “逐条 try/catch + 告警”而不是整体失败。

## EL-006：资产正确性靠数据库约束和事务，不靠内存判断

- 案例：并发拾取、装备交换、钱包扣减都出现过“先读后写”的竞态风险；最终用
  行锁、唯一索引、CHECK 约束和单事务解决，并有真实 PostgreSQL 并发测试。
- 经验：凡是“同一份资产只能属于一个地方”的规则，都要在数据库层表达；应用层
  判断只能作为快速失败，不能作为最终保证。
- 下次：新增商店/交易/邮件等资产路径时，先问“并发两次会发生什么”，再写测试。

## EL-007：tick 内禁止 IO，异步队列要有独立指标

- 案例：击杀奖励、拾取、装备全部走异步资产队列，tick 从不 await 数据库；
  50 人压测中 tick p95 与资产队列 p95（含排队）被分开观测，才能判断瓶颈在
  模拟还是事务。
- 经验：固定 tick 的性能问题不能靠“看起来不卡”判断；必须区分 tick 耗时、
  队列等待、SQL 耗时、网络发送。
- 下次：新增任何异步资产路径，都接入队列指标；压测报告必须同时给出 tick 与
  资产延迟。

## EL-008：大类拆分要行为等价、先补测试、分阶段

- 案例：`WorldMapRoom` 约 2,500 行；Alpha 0.1 只抽出 `SessionRegistry`、
  `CommandGuard`、`StateViewPublisher`，不改变协议、领域计算和错误码顺序，
  靠现有集成测试与 E2E 锁定行为；剩余编排明确列为 TD-SRV-01b。
- 经验：大重构不要与玩法开发同批进行；“抽取 + 等价 + 回归”一次只做一件事。
- 下次：拆分前先补“行为快照”测试；一次只移一个职责；移动后不改逻辑。

## EL-009：验收门禁必须在提交前真实执行

- 案例：多个阶段报告声称“全部通过”，但 CI 的 E2E job 从未真正执行；本地
  结果被当成 CI 结果。Alpha 0.1 补齐 PostgreSQL service 与连接串后，才具备
  可复现条件。
- 经验：报告只能写“实际执行过的命令与输出”。本地通过、远端未执行时必须
  明确标注，不能合并成“通过”。
- 下次：提交阶段代码前运行 `pnpm verify`；涉及浏览器行为时运行隔离 E2E；
  报告附命令、耗时、通过数。

## EL-010：数值与体验必须用试玩验证

- 案例：MVP 的三职业在数值表上有差异，但共用同一贴图、各只有 1 个技能、没有
  MP 回复，玩家实际体验不出职业差异；金币有产出无消耗，成长目标在 30 分钟后
  消失。
- 经验：系统“存在”不等于玩法“成立”。任何玩法切片都要用真实浏览器走一遍，
  记录操作次数、耗时、收益与挫败点。
- 下次：每个可玩切片附一份试玩记录（路径、截图、耗时、发现的问题），并在
  版本报告中回答“玩家能感受到什么”。

## EL-011：协议扩展优先加法，错误码要可行动

- 案例：自动攻击新增 `combat.engage` / `autoAttack.start|stop` 与
  `combat.target.changed`，复用既有命令幂等与限频；拒绝提示改成会消失的 Toast，
  并把“目标已死亡/冷却中”等可行动信息直接展示给玩家。
- 经验：协议变更尽量新增消息/字段，避免改语义；错误码必须对应玩家能采取的
  行动，而不是内部枚举名。
- 下次：新增消息前先检查能否复用现有命令管线；每个新错误码都要有中文提示与
  E2E/集成断言。

## EL-012：外键插入与行锁的顺序会造成死锁

- 案例：商店并发购买测试同时提交两笔交易。每个事务先插入 `asset_commands`
  （外键指向角色，PostgreSQL 取该行的 KEY SHARE 锁），再 `SELECT ... FOR UPDATE`
  同一角色行；两个事务都持有共享锁并同时申请排他锁，数据库检测到死锁并回滚
  其中一笔。
- 经验：同一事务内，涉及同一行的“外键引用”和“显式排他锁”必须保证稳定顺序。
  统一先锁聚合根（角色行），再写引用它的命令/流水/物品。
- 下次：新增资产命令时按“角色 → 命令幂等 → 资产行 → 流水”的顺序加锁，并用
  `Promise.allSettled` 并发测试验证只有一笔成功、余额不为负。

## EL-013：共享测试库的全局维护任务会制造偶发失败

- 案例：`purged expired` 用例在完整套件中偶发失败、单独运行稳定。测试库由
  所有 Vitest 文件共享；Game Server 集成测试启动的 Room 会周期清理过期掉落，
  可能删除另一个文件刚创建、正准备断言的掉落夹具。
- 经验：只要是“按时间/状态扫描全表”的维护任务，测试就不能假设表里只有自己
  的数据。断言要限定到本用例创建的 ID，或让维护任务按命名空间/地图隔离。
- 处理：资产集成测试的注入时钟改为从“当前时间 + 24 小时”起算，自己的掉落
  在真实清理任务看来始终未过期；测试推进时钟后再验证清理。不要用“重跑”掩盖。
- 下次：新增后台清理/归档任务时，同时设计测试隔离方式；看到“单独跑就过”的
  失败，先怀疑跨文件共享状态，而不是重跑掩盖。

## EL-014：共享契约与资产事务先单线打通，再按文件边界并行

- 案例：商店切片同时修改内容 schema、realtime 契约、钱包/账本事务、Room 和
  客户端。若按“服务端/客户端/内容”并行开工，协议字段、错误码和价格来源会
  反复返工；本轮先单线完成契约与事务，再补客户端与测试。
- 经验：涉及共享 DTO、迁移或资产事务的切片，先由集成角色单线定义并打通最小
  链路；美术、独立面板、纯数值配置可以在契约冻结后并行。
- 下次：拆任务时先标“共享接口/独占文件”，共享接口未冻结前不派并行写入。

## EL-015：修复一处锁顺序后必须审计同类入口

- 案例：Alpha 0.2 商店并发测试发现“先写幂等行（外键共享锁）再 `FOR UPDATE`”
  的死锁后，五个客户端资产命令都改了顺序，但 `grantKillReward` 仍保留旧顺序。
  独立审查指出了它，因为单 Room 的资产队列掩盖了问题。
- 经验：死锁、幂等、权限这类横切问题，修复点不是“调用方”，而是“所有同类入口”。
  修复后用 `grep` 列出同一张表/同一把锁的所有写入路径，逐条确认顺序。
- 下次：在 WORKLOG 的修复条目里列出审计到的入口清单；同类路径补并发测试，
  即使当前调用方式暂时不会触发。

## EL-016：幂等键的作用域必须与业务命令的作用域一致

- 案例：`asset_commands` 的幂等键按 `kind` 区分，账本键却只按
  `characterId + commandId`；同一 UUID 先买后卖时，第二笔账本插入撞唯一约束，
  整笔交易回滚为 `SERVICE_UNAVAILABLE`。
- 经验：一个事务里可能写多张幂等/流水表时，所有键必须使用同一组作用域字段；
  命令类型、角色、资产类型缺一不可。不同表的“看起来唯一”不代表语义一致。
- 下次：新增流水/幂等表时写下键的完整定义，并用“同一 commandId 跨操作复用”
  的回归测试验证，而不是只测同操作重放。

## EL-017：可选内容字段进入 diff 前必须处理 undefined

- 案例：第一次发布包含 `buyPrice`/`mpRegenPerSecond` 的 Content Release 时，
  验证接口返回 500。diff 比较旧版本（字段缺失）与新版本（字段存在），把
  `undefined` 传给 `canonicalJson`，而后者按设计拒绝 undefined 内容。
- 经验：“字段缺失”是可选内容字段的合法状态，diff/预览必须显式表示它；checksum
  仍应拒绝 undefined，避免非法内容进入发布。两者不是同一个序列化场景。
- 下次：新增可选内容字段时，同时补一条“旧版本缺失 vs 新版本存在”的 diff 测试，
  并实际走一遍保存草稿→校验→发布→激活，而不是只测单测。

## EL-018：内容存进 jsonb 后对象键顺序不可依赖

- 案例：Alpha 0.2 S2 技能切片中，战士技能栏把快捷键 2 的“铁布衫”排在快捷键 1
  “重击”之前。基线内容对象里的顺序本来正确，但 Content Release 的 payload 存在
  PostgreSQL `jsonb`，读回时按“键长度 + 字节”重排，`warrior_iron_skin` 比
  `warrior_heavy_strike` 短，于是排到了前面。单测直接使用内存对象，没暴露。
- 经验：`jsonb`/JSON 对象不承载顺序语义；只要 UI 或规则依赖顺序（技能栏、掉落
  表、任务步骤），就必须在读取后显式排序，并用“发布→读回”的路径验证。
- 下次：内容实体列表统一按业务字段（等级、快捷键、显示顺序）排序；新增内容
  列表时同时补一条断言顺序的单测或 E2E。数组本身有序，但不要把顺序寄托在
  `Record` 的键上。

## EL-019：并行 E2E 必须独占共享世界实体

- 案例：三职业外观切片新增的战士普攻用例与既有技能用例都攻击
  `wilds_slime_10`。单跑都通过；2 worker 全量回归时，两边争抢同一只史莱姆，
  技能用例持续看到 chase/return 而不是 attack，失败原因看起来像服务端 AI。
- 经验：E2E 的隔离不只包括数据库与端口，还包括地图上的怪物、掉落与刷点。共享
  实体在并行 worker 下会被拉扯、击杀或引走，产生与代码无关的假失败。
- 下次：新用例先 `grep` 该刷点/实体 ID 是否已被其他 spec 使用；选择独占刷点并
  在注释里写明原因；涉及共享世界状态的用例尽量放在 serial 分组。

## EL-020：可由权威快照派生的状态不要做成粘性缓存

- 案例：三职业外观切片中，客户端在收到 `death` 事件时把 `dead` 标记存在角色
  视觉对象上，等 `respawn` 事件清除。但 `respawn` 只发给复活者本人（复活后的
  HP/MP 属于私有信息），旁观者永远收不到清除信号，于是 A 一直看到 B 倒地；
  快照里 B 早已 `alive=true`。
- 经验：凡是快照每帧都会下发的状态（存活、位置、HP），客户端表现层应直接以
  快照为唯一事实，事件只做即时反馈（受击闪烁、死亡动作触发、音效）。事件是
  不完整、且通常只发给相关方的；把事件当作状态存储，迟早会在旁观者/重连/
  丢事件时卡住。
- 下次：新增表现状态时先问“它是否已经存在于快照”。若存在，就不要另建缓存；
  若必须缓存（如冷却、一次性动画），明确写出它的事件是否对所有观察者可见。

## EL-021：内容 Release 必须覆盖编译地图里的全部怪物引用

- 案例：S3 怪物威胁切片在 `starter_wilds` 新增白狼王/蜘蛛/石守卫刷点，新怪物
  先进入代码基线（`BASE_CONTENT_BUNDLE`）与编译地图，但开发区服仍激活旧
  Release `2026.11.26.2`。重启 Game Server 后，`ContentStore` 每 5 秒报
  “active content release failed validation”，原因是内容校验会拿当前编译地图
  的刷点去核对 Release 的怪物表：旧 Release 没有 `alpha_wolf` 等模板。
- 经验：地图刷点属于代码，怪物/物品模板属于内容 Release，但校验把它们当作
  同一份事实。代码侧新增刷点的部署必须与包含对应模板的 Release 发布成对出现；
  否则服务器不会使用旧 Release（保留上一个快照，启动时为基线 bundle），表现为
  持续报错且运营发布版本“看不见”。
- 下次：改动地图刷点或怪物模板时，按“编译地图 → 发布含新模板的 Release →
  激活 → 重启/新 Room”的顺序验收；把内容校验错误当作部署门禁，而不是忽略
  启动日志。发布脚本可增加“当前地图刷点引用是否被候选 bundle 覆盖”的预检。

## EL-022：新增内容 section 是 schema 变更，不是一次 JSON 编辑

- 案例：死亡代价需要一条全局规则，最初按“内容加一个可选字段”估算。实际落地
  涉及：`contentBundleSchema` 根部可选 section、`CONTENT_SECTIONS`/标签、
  `contentSectionDataSchemas` 与 `ContentSectionData` 类型、运营草稿更新的
  判别联合（`adminContentDraftUpdateSchema`）、PostgreSQL `content_section`
  枚举的新值与 expand 迁移，以及 `diff` 把 section 当作 `Record<id, entity>`
  的假设（`rules` 是单一设置对象，需要显式转成键值视图）。其中枚举与运营契约
  在编码前并不显眼。
- 经验：内容 section 在系统里是**schema 级**概念，不是一段自由 JSON。实体映射
  类 section 与设置类 section 的 diff/编辑语义不同；历史 Release 还要求新
  section 在 bundle 根部可缺省，否则 checksum 失效（EL-004）。
- 下次：新增 section 前先列出全部触点（contracts、基线内容、校验、枚举迁移、
  运营契约、diff/预览、消费方），并判断它是“实体集合”还是“设置对象”；设置类
  规则优先做成一个可扩展的 `rules` 对象字段，避免每加一条规则就新建 section。

## EL-023：新增内容校验规则先判断“历史数据是否必然满足”

- 案例：S4 装备切片新增“装备必须能获得”规则，最初写成 error。EL-004 的
  legacy payload 测试立刻失败（历史 Release 在商店价格出现前就存在），更严重
  的是 `ContentStore` 会在 Room 启动时重新校验数据库里的活动 Release：新规则
  一旦是 error，已发布的旧版本会直接无法加载，白狼王/扑击等线上内容随之消失。
  最终把该规则改为 warning，只保留“非装备设置 quality”这条历史数据不可能
  触发的新 error。
- 经验：内容校验同时服务两种场景——发布候选 bundle（可以严格）与加载历史
  Release（必须永远可读）。新增规则必须回答：旧 payload 是否一定满足？不确定
  就先用 warning，等历史版本退役后再升级为 error。
- 下次：改动 `packages/content-schema/src/validation.ts` 时，用 EL-004 的
  legacy payload 回归测试和一条“加载已存 Release”的集成路径同时验证；把
  “新 error 规则不得让历史 Release 失效”当成内容发布的默认门禁。

## EL-024：新增传送门会改变既有玩家的寻路与坐标用例

- 案例：S4-B 在静语荒野 `(13,10)` 放置废墟入口。该格既紧邻 PvP 决斗点
  `(12,10)/(13,10)`，又位于 autoAttack、economy 等用例从荒野入口前往怪物刷点
  的最短路径上。全量 E2E 中 Bob 被直接传送到废墟（PvP 用例失败），另外两个
  用例的攻击目标因玩家被传送而永远不结算。把入口改到主城西北角后，5 个失败
  全部消失。
- 经验：传送门是“会被动触发的全局状态”，它的格子会进入所有经过该格的 BFS
  路径；地图上新增传送门/刷点/可交互格时，不能只看怪物刷点分布，还要看测试
  与玩家常用路径、决斗点、NPC 站位等固定坐标。
- 下次：放置新传送门前 `grep` `tests/e2e` 的目标坐标与 `moveTo` 调用，并跑
  一遍最小相关用例；从全量 E2E 的失败坐标反查是否是传送触发（玩家出现在
  另一张地图/房间变化），不要先怀疑战斗或同步逻辑。

## EL-025：Playwright 测试文件不要在 ESM 顶层直接 import JSON

- 案例：物品图标切片的 E2E 需要从 `content/assets/manifest.json` 取帧号，最初
  写成 `import rawManifest from '../../content/assets/manifest.json'`。`vitest`
  与 `tsc` 都通过，但 `pnpm test:e2e` 在加载测试文件时直接失败：
  `Module "...manifest.json" needs an import attribute of "type: json"`。Playwright
  的 ESM 加载器不处理裸 JSON 导入，webServer 尚未启动就被判定失败。
- 经验：Vitest、TypeScript 与 Vite 都能解析 JSON 导入，但 Playwright 的测试
  运行时不保证；测试代码应把数据文件当数据读取，而不是依赖打包器的 JSON
  转换。注意 JSON 读取后的类型需要显式收窄（`Record<string, number>` 在
  `noUncheckedIndexedAccess` 下是 `number | undefined`）。
- 下次：E2E 读取内容/资源 JSON 时统一用 `readFileSync` + `JSON.parse`，并在
  断言前对缺失键给出明确错误；只把 JSON 导入留给应用代码（Vite/Vitest 链路）。

## EL-026：固定偏移的 HUD 层要和动态面板的最大高度一起算可点击性

- 案例：S4-D 右栏化 HUD 时把右侧面板起点从 208px 提到 112px，按“已连接”
  状态（连接卡片约 90px）视觉上留了空隙。全量 E2E 中 `shop.spec.ts` 稳定
  超时：断线状态多出 detail 行、meta 换行后连接卡片增至 124px，正好越过
  右栏起点 112px；「返回角色」按钮中心命中的是后渲染的 `minimap-heading`。
  改为在调试脚本里用 `document.elementFromPoint` 读取按钮中心的真实命中目标
  后定位，而不是继续猜测 z-index。
- 经验：叠加式 HUD 的“不重叠”不能只按最矮状态截图确认；绝对定位的相邻面板
  会随内容（连接状态、玩家数量、列表行）改变高度，视觉相邻不等于可点击。
  固定偏移应取目标面板在所有状态下最大高度 + 间隔。
- 下次：新增/移动 HUD 面板后，用 `boundingBox()` 与 `elementFromPoint` 抽查
  按钮中心，并覆盖“状态变化后”（断线、收起、窄屏）的尺寸；同时把点击可达性
  写成 E2E 断言（S4-D 的 `hud.spec.ts` 即为此）。

## EL-027：世界层标签避让用“纯布局函数 + 只读回读”，不要移动 Game Object

- 案例：S4-E 处理玩家、怪物与 NPC 名字标签重叠。最初考虑过把标签向上/下偏移
  或做屏幕网格避让，但标签跟随实体每帧移动，偏移会在擦肩时来回跳；最终改成
  纯函数 `resolveVisibleLabels`：输入屏幕矩形、优先级与距离，输出可见 id
  集合，场景只调用 `setVisible`。优先级为自己 > 目标 > NPC > 其他玩家 >
  怪物，同优先级按距离、再按 id 稳定排序；相交（含 3px 间距）即隐藏。
  同时新增 `labels()` 只读回读，E2E 直接断言“可见标签两两不重叠”，而不是靠
  截图肉眼判断。
- 经验：覆盖层拥挤时，先定义“谁该赢”的稳定优先级，再把布局做成不依赖
  Phaser 的纯函数；移动标签比隐藏标签更容易造成视觉抖动。任何视觉规则都应
  留一个只读回读入口，让浏览器测试能验证不变量，而不是验证实现细节。
- 下次：新增世界层 HUD/标签（掉落文字、传送门、任务标记）时，优先复用同一
  候选/优先级模型；若必须移动标签，至少保证同一实体的偏移在连续帧内稳定。

## EL-028：先分清 tick 长尾与稳态，再按子树剖面优化

- 案例：S4-F 的 50 人回归 tick p50 1.1ms、p95 14.75ms。第一反应容易去优化
  寻路或 GC；实际用生产构建 + `node --cpu-prof` 按 `simulateTick` 子树聚合后，
  tick 只占墙钟 2.9%，AOI 的重复刷新与每观察者 Set/数组分配占子树约 61%，
  战斗事件序列化/写入约 28%，`findPath` 只有 0.4%。改成每 tick 去重刷新 +
  复用 Set 后，p95 降到 5.34ms、p99 6.67ms。
- 经验：p95 远高于 p50 时先怀疑“同一 tick 内重复工作/分配”，不要平均优化所有
  可能热点；剖面必须按 tick 子树聚合自耗时，并区分测试客户端、IO 与服务器
  计算。优化前后用完全相同负载、相同构建方式对比。
- 下次：新增每 tick 批量任务（AOI、事件、掉落清理）时，先问“同一实体/观察者
  是否会在一 tick 内被重复处理”；批处理仍要在 tick 结束前 flush，保证下一 tick
  状态一致。

## EL-029：新增内容 section 是一份跨包清单，不是只改 schema

- 案例：S4-G 新增 `quests` section，schema、校验、`CONTENT_SECTIONS`、
  `contentSectionDataSchemas`、数据库枚举与基线内容都改完后，保存草稿仍然
  422。原因是 `contracts/admin.ts` 的 `adminContentDraftUpdateSchema` 是手写的
  section 判别联合，不随 `CONTENT_SECTIONS` 扩展；运行中的 Control API 只报
  “Invalid discriminator value”。补上 `quests` 分支并重启后，草稿、校验、发布、
  激活才全部通过。
- 经验：内容 section 的“新增清单”至少包括 contracts 的 section 枚举与数据
  schema、content-schema 的基线/校验/diff、persistence 的数据库枚举迁移、
  admin 草稿联合类型、运营界面标签，以及任何按 section 分支的脚本。类型检查
  能覆盖大部分，但 z.literal 联合的错误只在运行时出现；新增后应立刻用真实
  Control API 跑一次“保存草稿 → 校验”。
- 下次：把 section 清单写进 PR/切片检查表，或在 contracts 中用单一来源生成
  草稿联合类型；在此之前，任何新增 section 的验收都必须包含一次真实发布链路。

## EL-030：双人 E2E 必须显式加入同一 Room，`?fresh=1` 是“新建隔离房间”

- 案例：Alpha 0.3 S1 的组队 E2E 让两名玩家都用 `?fresh=1` 注册并进入主城，
  但 Alice 始终看不到 Bob 的玩家行。原因是 `?fresh=1` 走 `client.create`，
  每次都会创建一个新的 `world_map:starter_town` 房间实例；两人在地图上“同名
  同坐标”，却在两个不同的 Room 里。改为第一名玩家 `?fresh=1` 并从 HUD 的
  `room-id` 读取房间号，第二名玩家用 `?join=<roomId>` 加入同一房间后通过。
- 经验：E2E 里的“同图”不等于“同房间”。任何依赖两名玩家可见、聊天、组队、
  交易的用例，都必须显式建立同一个 Room；单玩家用例继续用 `?fresh=1` 隔离，
  避免与其他 spec 的世界实体互相干扰。
- 下次：新增多玩家用例时，先在断言前打印/断言双方的 `room-id` 相等；若测试
  在 20 秒内看不到对方，优先怀疑房间不一致，而不是 AOI 或渲染。

## EL-031：共享测试库里“第一个掉落实体”可能不是你的

- 案例：队伍共享掉落的集成测试从 `state.loot` 取第一个 key 去拾取，单独运行
  通过；全量并行运行时报 `NOT_OWNER`。原因是 Room 在启动时会恢复该地图上
  所有未领取掉落（`restoreLoot`），而共享测试库中其他测试文件留下的掉落也会
  被恢复进这个 Room；第一个掉落属于别的角色。改为按 `ownerId` 等于本次击杀者
  挑选后，全量 492 测试稳定通过。
- 经验：只要测试库是共享的，任何“从世界状态里取第一个”的用例都可能拿到别的
  文件创建的实体；掉落、怪物、玩家都应通过本用例已知的 id/归属来筛选。房间
  启动恢复数据会让这种跨文件泄漏变得可见，但根因是测试没有限定自己的实体。
- 下次：新增掉落/拾取类测试时，先按归属者或击杀引用筛选；涉及拾取距离的用例，
  先读取掉落坐标并移动过去，因为怪物可能在追击中死亡，掉落不在刷点位置。

## EL-032：跨 Room 的关系状态要“宿主上报 + 按宿主路由”

- 案例：队伍最初存在地图 Room 里，过图等于离开旧 Room、加入新 Room，队伍
  因此在传送瞬间散掉。把队伍上移到进程级后，Room 仍然拥有会话与战斗状态，
  只负责两件事：上报本 Room 成员的 presence（等级/HP/存活/在线/所在 Room），
  以及把服务路由过来的名单快照与邀请投递给本 Room 的玩家。传送时保留席位并
  标记离线，目标 Room 加入后恢复；只有真正离开世界才移出队伍。
- 经验：判断状态该放哪一层，看它的生命周期是否长于 Room。关系（队伍、好友、
  公会）通常比“玩家此刻在哪张地图”活得更久，就不应塞进 Room；Room 只做宿主
  适配。跨 Room 的列表要由“宿主上报 + 服务按宿主路由”，不要让每个 Room 试着
  读取别人的会话；同时把“离开 Room”和“离开世界”分成两个语义，否则传送、
  崩溃与主动退出会被同一段清理代码误伤。
- 下次：新增好友、公会、跨图私聊或副本队伍时，沿用“进程级关系表 + presence
  上报 + Room 端口”的形状；需要重启保留或多进程时，再把状态换成持久化或共享
  存储，并先写 ADR（TD-SRV-11）。

## EL-033：过图后的第一条客户端指令要在重新加入完成后再发

- 案例：S2 的 8584 真实浏览器脚本在 `session.transfer` 到达、地图名已变成
  `ruined_fields` 之后立即调用 `moveToTile(22,30)`。调试钩子返回 `true`，但
  角色 12 秒后仍在出生点；此时新 Room 尚未加入完成，`sendMove` 被丢弃。
  E2E 用例里同样的动作没有失败，因为它额外等待了
  `connection-status=connected`。
- 经验：地图名、房间号或快照变化只说明“收到过传送消息”，不说明新 Room 已
  可用。任何跨图后的输入、拾取、战斗和调试钩子，都必须以“连接状态回到
  connected”为前置条件；调试钩子的布尔返回值只表示“调用了”，不表示服务端
  接受了意图。
- 下次：写真实浏览器脚本时，把 `connected` 等待封装进 `moveTo`/`attack` 辅助
  函数，而不是依赖调用方的记忆。

## EL-034：生成物提交前要跑仓库的格式化

- 案例：`pnpm maps:compile` 按 `JSON.stringify(map, null, 2)` 写编译地图，
  而仓库里的已提交文件是 Prettier 的换行格式。直接提交时三张地图产生
  1.7 万行“格式改动”，真正的刷点变更只有一行。对生成文件执行
  `pnpm exec prettier --write content/maps/compiled/*.json` 后，其他地图恢复
  原样，`ruined_fields` 的差异收敛为新增刷点。
- 经验：生成命令与提交格式不一定一致；提交生成物前先跑 `format:check`，让
  差异只包含真实变化。检查点包括编译地图、图标图集与任何代码生成的 JSON。
- 下次：修改 Tiled 源图后固定执行“编译 → Prettier → 查看 `git diff --stat`”，
  若行数异常放大，先怀疑格式而不是内容。

## EL-035：重寻路不能先回格中心，否则每一步都在后退

- 案例：S2 后试玩反馈“点怪物后每走几步卡顿一下、连续点击地面不流畅”。服务器
  的 `setPath` 与客户端的路径构建都会在玩家处于格内偏移时先插入当前格中心，
  以保证轴对齐；自动攻击每 350ms 重算一次接近路径，于是玩家每 1.4 格就被拉回
  当前格中心，最多后退 500 单位。寻路本身是最短 BFS；问题在路径执行。
- 经验：格内偏移状态是正常的移动状态，不是错误。新路径与当前偏移同向时继续
  直行；垂直转向时在下一格内转弯（先沿当前轴进入下一格，再对齐中心），不要
  回到旧格中心。所有线段仍轴对齐、仍不穿阻挡格，但走出来的路线与 BFS 路径一致。
- 下次：任何“重设路径”的实现都要问两个问题：玩家现在是否在格内偏移？新路径
  的第一段是否与当前偏移同向？只对真正的反向/对角情况做中心对齐。

## EL-036：自动攻击必须有路径预测，不能只跟随状态快照

- 案例：点击怪物后角色由服务端自动接近，但服务器只把移动写进状态快照
  （10Hz），没有把接近路径发给客户端。客户端没有路径可预测时，只能按快照
  插值，表现成每 100ms 跳一步的阶梯移动；这被玩家描述为“追击时卡顿”。
- 经验：凡是由服务端发起的持续移动（自动攻击、寻路追击、击退），都要像
  `command.ack` 一样把权威路径推给客户端，让客户端在路径上按速度预测；快照只
  用于校正。路径事件用增量字段（可选 `path`/`startX`/`startY`/速度）保持向后
  兼容，客户端裁剪已走过的节点后复用同一套预测逻辑。
- 下次：新增任何服务端驱动位移时，先问“客户端怎么知道下一段路”，没有答案就
  会退化成快照跟随；同时给集成测试加“位置不倒退”和浏览器加“连续移动不冻结”
  两条断言。

## EL-037：可重置状态用“周期键 + 纯函数”表达，不要删除或改写历史行

- 案例：每日任务第一版设计容易滑向“交付后把任务行重置为可接取”，但这样会
  丢掉历史、把重置与交付的并发塞进同一行，还要额外处理在线玩家跨日。采用
  `period_key` 后，每个周期是独立一行，唯一约束仍能阻止同周期重复接取；
  当前周期由 `dailyPeriodKey(now, rule)` 计算，旧周期行只作为历史。
- 经验：凡是“按天/周/赛季重来”的状态，优先把它建模成不可变的历史行 + 当前
  周期键，而不是可变的重置字段。重置边界做成注入时钟的纯函数，既能用固定
  时间做确定性测试，也不依赖宿主机时区；视图层把非当前周期的记录视为不存在，
  旧记录就不会意外参与进度或奖励。
- 附带教训：新增一条“跨 section 的内容约束”（日常必须有 `rules.dailyReset`）
  会让“删除 rules 的旧 Release 夹具”失效。修改内容校验时，先搜索所有构造
  旧 Release 的测试，并让夹具真正回到旧版本（同时移除它不可能拥有的新内容）。
- 下次：任何重复周期/赛季机制，先写时间函数与边界测试，再写表结构；重置
  不要用后台任务清理，除非历史增长已被度量（本轮记为 TD-DATA-12）。

## EL-038：自动化要复用意图与事务，跨地图状态让客户端重放

- 案例：一键任务导航第一版很容易写成“服务器直接带玩家走路、到点自动发奖”，
  但这样会出现第二套移动/战斗/发奖语义，也无法解释失败。最终实现为：
  客户端提交 hunt/return/stop 意图，服务器状态机计算路线并复用既有自动攻击；
  到达后仍由客户端发送既有 `quest.claim`，奖励事务、幂等与距离校验不变。
- 经验：凡是“自动完成某个玩法”的需求，先问“它复用了哪条既有意图与哪个既有
  事务”。如果没有答案，就会长出旁路。跨 Room 的状态（过图、重连）不要硬塞进
  新 Room；让客户端在新连接上重放幂等意图，服务器重新校验，比共享状态简单。
- 测试：自动战斗会主动抢共享世界里的怪，无法遵守“独占刷点”约定。给自动化
  E2E 一个独立房间实例（本轮的 `?freshTransfer=1`）比加长超时更可靠。
- 附带教训：只要界面会展示另一张地图上的 NPC/地点，名字解析就必须来自全部
  地图，不能只来自玩家当前地图；否则野外会露出 `town_guard` 这类机器名。

## EL-039：数据已经全量下发时，先检查客户端的过滤条件

- 案例：服务器本来就会把全部任务（含其他地图发布的任务）下发给客户端，但
  任务面板按“当前地图 NPC”过滤，结果野外看不到主城的可接任务。修复是删除
  客户端过滤并补一张发布者→地图的本地解析表，不需要协议或服务端改动。
- 经验：遇到“某个信息在别处看不到”时，先确认它是否已经在下发数据里；如果
  是，问题通常在展示层的过滤/索引，而不是后端缺失。跨地图的名字、地点与
  入口都应该是全局解析，不能只解析当前地图。
- 附带：远程接取没有新增“远程直接发奖”的旁路，而是给既有导航状态机增加一个
  `accept` 目的，走真实传送门与既有接取命令；这保持了服务端权威与资产事务。

## EL-040：地图 NPC 属于代码发布，先重启再校验引用它的内容

- 案例：废墟斥候已写进 `content/maps/ruined_fields.tmj` 并编译，但内容校验
  读取的是运行中 Control API 进程启动时加载的编译地图。保存含 `ruins_scout`
  的任务草稿后，validate 返回 5 条“发布 NPC 不在任何地图中”；重启开发栈后
  同一草稿 0 issue。
- 经验：内容 Release 只覆盖 quests/items 等 section，地图 NPC、怪物刷点与
  角色枚举属于代码与编译产物。顺序固定为：编译地图 → 部署/重启引用地图的服务
  → 再保存、校验、发布引用新 NPC 的内容。校验报“NPC 不存在”时，先确认进程
  是否加载了最新编译产物，不要为了迁就旧进程去改内容。
- 附带：地图编译器直接使用 `MAP_NPC_ROLES` 契约枚举校验角色，新增角色只需改
  一处；编译产物仍需运行 Prettier 才能通过 `format:check`。

## EL-041：批量客户端脚本的 teardown 必须有界

- 案例：50 人容量 sanity 中，一名 mover 走进荒野的返回传送门，被服务端传到
  主城；SDK 对这个已结束的 Room 调用 `leave()` 永不 settle。报告 JSON 已经
  写出，但脚本一直挂到外部超时，看起来像“容量测试失败”。
- 经验：压测/巡检脚本的退出路径要和服务端主动操作（传送、踢出、封禁）兼容。
  结束阶段用有界等待（`Promise.race` + 超时），随后关闭仍打开的连接；不要让
  “写报告成功”被 teardown 挂起抵消。报告与退出码是两件事，二者都要验证。
- 测试：修完先用 10 人 × 15 秒 smoke 验证退出码 0，再跑正式 50 人 × 2 分钟
  门禁；两次都要确认 `EXIT:0`。

## EL-042：收集类目标用“背包即进度”，在交付事务里扣物品

- 案例：S3-D1 把任务目标从击杀扩展到收集。第一版最容易写成“拾取时记进度、
  交付时只看进度”；这样材料卖掉后进度仍显示完成，每日任务还能用同一批材料
  反复交付。第二版是“拾取时记进度 + 交付扣物品”，又需要在拾取、购买、任务
  奖励、商店回收等所有获取路径挂钩，卖掉材料后还要处理进度倒退。最终实现为
  视图从背包汇总派生（不写任务进度），交付事务 `FOR UPDATE` 锁住该模板堆叠、
  扣除物品、把行从 active 推到 completed → claimed 并发放奖励，全部在一个
  事务；数量不足返回 `QUEST_ITEMS_MISSING` 并回滚。Room 只在资产命令提交后
  重发任务快照。
- 经验：凡是“把 N 个已有资源交出去”的目标，进度的事实来源就是当前持有量，
  状态在读取时派生；任务的唯一写入点是交付事务。不要在多个获取路径上散落
  进度写库，否则迟早出现“进度与背包不一致”。
- 附带：每日任务要求商店可购买的物品会形成“金币买物品换金币奖励”的套利，
  内容校验要显式禁止；一次性教学任务可以例外，但仍要验证奖励低于成本。
- 下次：新增到达、使用、护送等目标时，先回答“进度的事实来源是什么、唯一
  写入点在哪、失败如何回滚”，再定义 schema。

## EL-043：自动化要复用既有事务，测试要为自动化改写而不是抢时序

- 案例：S3-E 的自动拾取在 Room 的 tick 里为归属者提交 `AssetService.pickup`，
  没有新增资产写入路径；但旧的集成/E2E 用例默认“击杀后手动点掉落”，自动化后
  手动命令与 200ms 的自动 tick 互相抢时序：有时手动赢，有时掉落已经被吸走。
  首领集成测试还因共享测试库里残留的旧掉落提前满足“地面有掉落”，在归属者
  奖励事务提交前就取了快照。
- 经验：新增自动化时，先列出所有假设“玩家会手动执行”的测试，把它们改成断言
  自动化结果（背包直接出现物品、广播与状态消失），而不是保留手动命令去和
  自动化赛跑。确实需要测试手动路径（如队伍共享兜底）时，给 Room 一个显式的
  测试开关关闭自动化，并在测试里说明原因。
- 附带：判断“某个实体存在”的等待条件必须锁定本次用例创建的实体；共享测试库
  里 `.size > 0` 很容易被历史数据提前满足。
- 下次：任何 tick 驱动的自动化都要问三个问题：复用哪个事务？和玩家命令如何
  排队？哪些测试会因此变成竞态？
