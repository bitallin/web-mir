# Web Legend 工程经验记录

- 目的：把真实项目中反复出现、代价高昂或验证有效的经验沉淀下来，避免同类问题
  第二次出现时重新踩坑。
- 规则：每条经验必须有实际案例或证据；只写“为什么”和“下次怎么做”，不写泛泛
  而谈的原则。需要所有 Agent 强制遵守的，才提炼进 `AGENTS.md`。
- 维护：由 Tech Lead 在里程碑/复盘时追加；不删除历史条目，过时可标注“已失效”。

## EL-001：独立端口不等于独立环境

- 案例：阶段 10 审计中，E2E 使用独立端口（5184/5185/3086/2587）但仍写开发库；
  开发栈的 Control API 与 E2E 的 Control API 共用 `outbox_events`，开发进程抢走
  kick 命令并投递给不含该会话的 87 端口，`applied=0` 仍标记成功，测试假失败。
- 经验：隔离必须覆盖**所有共享状态**——数据库、Outbox、内容激活、Redis、
  文件系统、端口。只换端口或只换进程不算隔离。
- 下次：新增测试栈时列出“它会写哪些共享状态”，逐项隔离；E2E 默认一次性数据库
  并在结束时删除（ADR-025）。

## EL-002：测试结果的“看起来通过”比失败更危险

- 案例：内容发布 E2E 里有 `expect(x).toBeDefined(); if (x === undefined) return;`
  的“空通过”分支；容量报告把 `LOAD_ATTACKERS` 误读成额外玩家，导致“30+10”
  被高估为 40 人。
- 经验：门禁必须断言“目标行为确实发生”，而不是“没有报错”。指标口径必须写进
  脚本输出，不能只存在于口头理解。
- 下次：每个 E2E 至少断言一个用户可见结果或数据库结果；压测脚本显式打印
  玩家/攻击者/时长/接受率/拒绝码，并断言接受率下限。

## EL-003：React updater 里做副作用会静默丢执行

- 案例：Alpha 0.1 的 Toast 去重标记写在 `setState(updater)` 内部，并依赖 updater
  里的 `setTimeout`；React 异步执行 updater，定时器从未安排，提示永不消失。
- 经验：状态更新函数必须是纯函数。去重、定时器、日志、网络请求都放在
  updater 之外，用同步读取的 ref 或先算后写。
- 下次：涉及定时消失的 UI，E2E 必须断言“出现后在 N 秒内消失”，而不是只断言
  出现。

## EL-004：内容 schema 加字段会改变历史 Release 的 checksum

- 案例：为商店给物品增加 `buyPrice/sellPrice` 时，若使用 Zod `.default(0)`，
  旧 Release 的 payload 在解析后被补上默认字段，canonical JSON 变化，checksum
  与库中记录不一致；`ContentStore` 会拒绝该 Release 并沿用旧快照。
- 经验：内容 schema 的演进要考虑**不可变历史数据**。可选字段用 `.optional()`，
  在代码里用 `?? 0` 解读；只有确认能重算/重发所有历史 Release 时才能用
  `.default()` 或改 `schemaVersion`。
- 下次：修改 `content-schema` 后，用一条真实历史 payload 做“解析→checksum”
  回归测试；新增字段的兼容策略写进 ADR。

## EL-005：运营可以直接制造登录事故

- 案例：内容发布删除一个仍被玩家持有的物品模板后，持有者加入世界时报
  “资产加载失败”，整个地图的未领取掉落也可能停止恢复（TD-DATA-04）。
- 经验：任何“可删除被引用的内容”都必须做引用完整性校验；加载路径必须逐条
  容错，不能一条坏数据拖垮整批。
- 下次：内容发布前查询 `item_instances` 的 distinct 模板；批量加载用
  “逐条 try/catch + 告警”而不是整体失败。

## EL-006：资产正确性靠数据库约束和事务，不靠内存判断

- 案例：并发拾取、装备交换、钱包扣减都出现过“先读后写”的竞态风险；最终用
  行锁、唯一索引、CHECK 约束和单事务解决，并有真实 PostgreSQL 并发测试。
- 经验：凡是“同一份资产只能属于一个地方”的规则，都要在数据库层表达；应用层
  判断只能作为快速失败，不能作为最终保证。
- 下次：新增商店/交易/邮件等资产路径时，先问“并发两次会发生什么”，再写测试。

## EL-007：tick 内禁止 IO，异步队列要有独立指标

- 案例：击杀奖励、拾取、装备全部走异步资产队列，tick 从不 await 数据库；
  50 人压测中 tick p95 与资产队列 p95（含排队）被分开观测，才能判断瓶颈在
  模拟还是事务。
- 经验：固定 tick 的性能问题不能靠“看起来不卡”判断；必须区分 tick 耗时、
  队列等待、SQL 耗时、网络发送。
- 下次：新增任何异步资产路径，都接入队列指标；压测报告必须同时给出 tick 与
  资产延迟。

## EL-008：大类拆分要行为等价、先补测试、分阶段

- 案例：`WorldMapRoom` 约 2,500 行；Alpha 0.1 只抽出 `SessionRegistry`、
  `CommandGuard`、`StateViewPublisher`，不改变协议、领域计算和错误码顺序，
  靠现有集成测试与 E2E 锁定行为；剩余编排明确列为 TD-SRV-01b。
- 经验：大重构不要与玩法开发同批进行；“抽取 + 等价 + 回归”一次只做一件事。
- 下次：拆分前先补“行为快照”测试；一次只移一个职责；移动后不改逻辑。

## EL-009：验收门禁必须在提交前真实执行

- 案例：多个阶段报告声称“全部通过”，但 CI 的 E2E job 从未真正执行；本地
  结果被当成 CI 结果。Alpha 0.1 补齐 PostgreSQL service 与连接串后，才具备
  可复现条件。
- 经验：报告只能写“实际执行过的命令与输出”。本地通过、远端未执行时必须
  明确标注，不能合并成“通过”。
- 下次：提交阶段代码前运行 `pnpm verify`；涉及浏览器行为时运行隔离 E2E；
  报告附命令、耗时、通过数。

## EL-010：数值与体验必须用试玩验证

- 案例：MVP 的三职业在数值表上有差异，但共用同一贴图、各只有 1 个技能、没有
  MP 回复，玩家实际体验不出职业差异；金币有产出无消耗，成长目标在 30 分钟后
  消失。
- 经验：系统“存在”不等于玩法“成立”。任何玩法切片都要用真实浏览器走一遍，
  记录操作次数、耗时、收益与挫败点。
- 下次：每个可玩切片附一份试玩记录（路径、截图、耗时、发现的问题），并在
  版本报告中回答“玩家能感受到什么”。

## EL-011：协议扩展优先加法，错误码要可行动

- 案例：自动攻击新增 `combat.engage` / `autoAttack.start|stop` 与
  `combat.target.changed`，复用既有命令幂等与限频；拒绝提示改成会消失的 Toast，
  并把“目标已死亡/冷却中”等可行动信息直接展示给玩家。
- 经验：协议变更尽量新增消息/字段，避免改语义；错误码必须对应玩家能采取的
  行动，而不是内部枚举名。
- 下次：新增消息前先检查能否复用现有命令管线；每个新错误码都要有中文提示与
  E2E/集成断言。

## EL-012：外键插入与行锁的顺序会造成死锁

- 案例：商店并发购买测试同时提交两笔交易。每个事务先插入 `asset_commands`
  （外键指向角色，PostgreSQL 取该行的 KEY SHARE 锁），再 `SELECT ... FOR UPDATE`
  同一角色行；两个事务都持有共享锁并同时申请排他锁，数据库检测到死锁并回滚
  其中一笔。
- 经验：同一事务内，涉及同一行的“外键引用”和“显式排他锁”必须保证稳定顺序。
  统一先锁聚合根（角色行），再写引用它的命令/流水/物品。
- 下次：新增资产命令时按“角色 → 命令幂等 → 资产行 → 流水”的顺序加锁，并用
  `Promise.allSettled` 并发测试验证只有一笔成功、余额不为负。

## EL-013：共享测试库的全局维护任务会制造偶发失败

- 案例：`purged expired` 用例在完整套件中偶发失败、单独运行稳定。测试库由
  所有 Vitest 文件共享；Game Server 集成测试启动的 Room 会周期清理过期掉落，
  可能删除另一个文件刚创建、正准备断言的掉落夹具。
- 经验：只要是“按时间/状态扫描全表”的维护任务，测试就不能假设表里只有自己
  的数据。断言要限定到本用例创建的 ID，或让维护任务按命名空间/地图隔离。
- 处理：资产集成测试的注入时钟改为从“当前时间 + 24 小时”起算，自己的掉落
  在真实清理任务看来始终未过期；测试推进时钟后再验证清理。不要用“重跑”掩盖。
- 下次：新增后台清理/归档任务时，同时设计测试隔离方式；看到“单独跑就过”的
  失败，先怀疑跨文件共享状态，而不是重跑掩盖。

## EL-014：共享契约与资产事务先单线打通，再按文件边界并行

- 案例：商店切片同时修改内容 schema、realtime 契约、钱包/账本事务、Room 和
  客户端。若按“服务端/客户端/内容”并行开工，协议字段、错误码和价格来源会
  反复返工；本轮先单线完成契约与事务，再补客户端与测试。
- 经验：涉及共享 DTO、迁移或资产事务的切片，先由集成角色单线定义并打通最小
  链路；美术、独立面板、纯数值配置可以在契约冻结后并行。
- 下次：拆任务时先标“共享接口/独占文件”，共享接口未冻结前不派并行写入。

## EL-015：修复一处锁顺序后必须审计同类入口

- 案例：Alpha 0.2 商店并发测试发现“先写幂等行（外键共享锁）再 `FOR UPDATE`”
  的死锁后，五个客户端资产命令都改了顺序，但 `grantKillReward` 仍保留旧顺序。
  独立审查指出了它，因为单 Room 的资产队列掩盖了问题。
- 经验：死锁、幂等、权限这类横切问题，修复点不是“调用方”，而是“所有同类入口”。
  修复后用 `grep` 列出同一张表/同一把锁的所有写入路径，逐条确认顺序。
- 下次：在 WORKLOG 的修复条目里列出审计到的入口清单；同类路径补并发测试，
  即使当前调用方式暂时不会触发。

## EL-016：幂等键的作用域必须与业务命令的作用域一致

- 案例：`asset_commands` 的幂等键按 `kind` 区分，账本键却只按
  `characterId + commandId`；同一 UUID 先买后卖时，第二笔账本插入撞唯一约束，
  整笔交易回滚为 `SERVICE_UNAVAILABLE`。
- 经验：一个事务里可能写多张幂等/流水表时，所有键必须使用同一组作用域字段；
  命令类型、角色、资产类型缺一不可。不同表的“看起来唯一”不代表语义一致。
- 下次：新增流水/幂等表时写下键的完整定义，并用“同一 commandId 跨操作复用”
  的回归测试验证，而不是只测同操作重放。

## EL-017：可选内容字段进入 diff 前必须处理 undefined

- 案例：第一次发布包含 `buyPrice`/`mpRegenPerSecond` 的 Content Release 时，
  验证接口返回 500。diff 比较旧版本（字段缺失）与新版本（字段存在），把
  `undefined` 传给 `canonicalJson`，而后者按设计拒绝 undefined 内容。
- 经验：“字段缺失”是可选内容字段的合法状态，diff/预览必须显式表示它；checksum
  仍应拒绝 undefined，避免非法内容进入发布。两者不是同一个序列化场景。
- 下次：新增可选内容字段时，同时补一条“旧版本缺失 vs 新版本存在”的 diff 测试，
  并实际走一遍保存草稿→校验→发布→激活，而不是只测单测。

## EL-018：内容存进 jsonb 后对象键顺序不可依赖

- 案例：Alpha 0.2 S2 技能切片中，战士技能栏把快捷键 2 的“铁布衫”排在快捷键 1
  “重击”之前。基线内容对象里的顺序本来正确，但 Content Release 的 payload 存在
  PostgreSQL `jsonb`，读回时按“键长度 + 字节”重排，`warrior_iron_skin` 比
  `warrior_heavy_strike` 短，于是排到了前面。单测直接使用内存对象，没暴露。
- 经验：`jsonb`/JSON 对象不承载顺序语义；只要 UI 或规则依赖顺序（技能栏、掉落
  表、任务步骤），就必须在读取后显式排序，并用“发布→读回”的路径验证。
- 下次：内容实体列表统一按业务字段（等级、快捷键、显示顺序）排序；新增内容
  列表时同时补一条断言顺序的单测或 E2E。数组本身有序，但不要把顺序寄托在
  `Record` 的键上。
