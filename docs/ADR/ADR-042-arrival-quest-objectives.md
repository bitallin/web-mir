# ADR-042：到达类任务目标与位置裁定

- 状态：Accepted
- 日期：2026-11-27
- 阶段：Alpha 0.3 S3-D2（任务目标类型扩展）
- 关联：ADR-016（服务端移动）、ADR-034（内容驱动任务链）、ADR-038（每日任务）、
  ADR-039（一键任务导航）、ADR-040（收集任务）、ADR-041（怪物归属）

## 1. 背景

Alpha 0.3 的任务只有“击杀”和“收集”两种动词：击杀把玩家带到刷点，收集把玩家
带到掉落来源。两者都会结束于战斗，地图只作为背景。S3-D2 计划加入“到达地点”
目标，让探索本身成为任务目标，并给一键导航一个不依赖怪物的用途。

## 2. 问题

1. **谁判定到达**：客户端知道自己的预测位置，但位置必须由服务端裁定；客户端
   上报“我已到达”会直接制造一个可伪造的完成条件。
2. **什么时候写进度**：到达是一次性事件，离开区域后不应撤销；不能像收集任务
   那样从当前位置派生，否则玩家走开就回到未完成。
3. **写在哪里**：到达不改变物品、金币或经验，但必须持久化，重登后仍显示完成；
   它是否应该占用资产命令与幂等键？
4. **与每日任务的关系**：日常需要按重置周期隔离；旧周期的到达行不能在新一天
   被误判完成。
5. **一键导航**：现有 `hunt` 目的只认识怪物；到达任务需要走到地图坐标，跨图时
   仍走传送门，不能瞬移。
6. **内容安全**：目标坐标必须在地图内且可行走，否则任务永远无法完成。
7. **校验成本**：每个 tick 扫描所有玩家会浪费 CPU；但也不能把数据库写入放进
   20Hz 循环。

## 3. 备选方案

1. **客户端上报“已到达”**：实现最省事，但违反服务端权威；一个改包的客户端可以
   完成任意到达任务。
2. **移动 ack 时判定**：只在手动移动命令完成时检查。服务端自动寻路、登录时已在
   区域内的角色、被击退等路径会漏判，需要额外补事件。
3. **每次 tick 精确扫描并同步写库（否决）**：判定最新，但 tick 内等待 SQL 违反
   架构原则。
4. **独立 `character_quest_visits` 表**：语义清楚，但任务进度已经在
   `character_quests.progress`，多一张表只会引入第二套状态。
5. **服务端位置扫描 + 异步事务（采纳）**：Room 以 4Hz 读取自己已维护的权威
   位置，命中后把完成写入既有任务行；tick 不等待数据库。

## 4. 决策

1. **内容契约**：`questObjectiveSchema` 增加闭集分支
   `{ kind: 'reach', mapId, tile: { x, y }, radiusTiles }`，半径 1–5。视图增加
   `{ kind: 'reach', mapId, mapName, tile, radiusTiles }`，地图名由服务端从编译
   地图解析；客户端不自行拼接地图数据。
2. **判定规则**：领域纯函数 `reachObjectiveMet(objective, mapId, position)` 只在
   地图匹配且玩家所在格与目标格的直线距离 ≤ `radiusTiles` 时为真。位置来自
   `WorldSimulation`，不读取任何客户端字段。
3. **观测位置**：每个地图 Room 每 4 个 tick（20Hz 下 5Hz 周期）扫描一次在线
   会话；只检查 `active` 的到达任务和当前地图的目标。命中后通过资产队列调用
   `AssetService.completeReachQuest`，并在飞行中去重、失败退避 2 秒后重试。
4. **持久化**：`completeReachQuest` 在事务内先锁角色行（与接取/交付一致），再
   `FOR UPDATE` 读取当期任务行；只有 `active` 行会写 `progress = 1`、
   `status = completed`、`completedAt`。重复观测或并发观测是幂等的；已
   `completed/claimed` 的行原样返回。
5. **不新增资产命令**：到达不改变任何资产，不需要金币账本或物品事务。幂等性
   由角色行锁与“只更新 active 行”的条件共同保证；`character_quests` 的
   `version` 与时间戳仍是审计痕迹。
6. **每日隔离**：完成事务按内容 `rules.dailyReset` 计算当前周期键，只更新当前
   周期的行；Room 扫描时也跳过 `periodKey` 与当前周期不符的旧行。
7. **导航**：沿用 `quest.navigate` 的 `hunt` 目的表示“前往目标”，到达任务不走
   自动攻击。服务端按目标地图做传送门路由；同图时用
   `findApproachPath(runtime, target, from, radius)` 选最短可达落脚点。进入半径
   后清空路径并等待完成事务；完成后以 `quest.navigation: completed` 停止。
8. **内容校验**：目标地图必须存在；坐标在地图范围内；目标格必须可行走；半径
   必须在 1–5。校验不检查“从出生点是否可达”，可达性由导航在运行时报告。
9. **客户端**：任务面板与追踪器显示“到达 地图名（x,y）”和“已到达/未到达”；
   行动按钮在 `reach` 目标上显示「前往探索」，文案不再假设一定会战斗。

## 5. 后果

- 无数据库迁移：复用既有 `character_quests.progress/status/completed_at`。
- 历史 Release 不含到达目标，schema 的加法扩展不影响其解析与 checksum；
  新内容需要发布并激活后才会下发给玩家。
- 到达是唯一不需要客户端命令的任务完成路径；Room 只信自己的模拟位置，伪造
  协议无法完成。
- 扫描成本与在线人数线性相关，每 4 tick 一次；没有数据库读取，只有命中的
  少数会话进入资产队列。
- 到达任务在开放 PvP 地图上仍然有旅途风险；这是玩法的一部分，不提供瞬移或
  无敌保护。
- 未覆盖：世界内的目标光柱/小地图标记（TD-CLI-24）、组队共享到达进度、任务
  放弃与任务日志。
