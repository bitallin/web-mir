# ADR-035：组队是房间内状态，共享经验走独立幂等事务

- 状态：Accepted（已由 ADR-036 修订）
- 日期：2026-11-27
- 阶段：Alpha 0.3 S1（社交基础）
- 修订：ADR-036 将队伍状态从“每个 Room 一份”提升为进程级服务；本文关于
  “传送/离开 Room 即结束队伍”的描述以 ADR-036 为准，其余规则不变。
- 关联：ADR-003（每地图固定 Room）、ADR-008（Room 固定内容快照）、
  ADR-020（资产事务与幂等）、ADR-022（内容发布）、ADR-025（Room 拆分）、
  ADR-031（内容化规则）、TD-DATA-11（经验无流水）、TD-SRV-03（资产单队列）

## 1. 背景

`docs/GAMEPLAY_REVIEW.md` 把“多人交互”评为 2/5：玩家能看见彼此、聊天、决斗，
但没有合作目标；`docs/PROJECT_ROADMAP.md` 把组队列为 Alpha 0.3 的核心留存
系统。任务是“一个人做什么”，组队是“为什么和另一个人一起做”，在继续堆任务、
副本或交易之前，先把最小的合作关系交付出来，风险更低、反馈更直接。

本切片只交付：邀请/接受/拒绝/离开、队伍名单、同图共享击杀经验。不做队伍
聊天、跨图组队、掉落分配、队长移交界面、公会或好友。

## 2. 问题

1. **状态放在哪里？** 组队是临时社交关系，不是资产；若进入 PostgreSQL，就要
   处理进程崩溃、Room 迁移、重连与清理任务。当前每张地图只有一个固定 Room
   （ADR-003），队伍天然以 Room 为边界。
2. **谁能看见？** 公开 Room State 会被所有同图玩家读取，队伍名单（等级、HP、
   在线状态）不应进入公开状态；隐藏 `players` 字段又会影响 AOI 与战斗。
3. **共享经验会不会制造经济漏洞？** 击杀奖励已是一次事务（经验、金币、掉落、
   任务进度）；如果让队友“再领一次击杀”，就会重复掷掉落、重复发金币、重复
   推进任务。共享必须是确定性的分享，而不是第二次抽奖。
4. **跨图与断线怎么办？** 传送是“离开旧 Room、重新加入新 Room”；断线有 15 秒
   宽限。队伍需要明确的归属与清理规则，不能出现幽灵成员。
5. **怎么防止刷经验与误操作？** 邀请范围、队伍上限、邀请过期、重复命令、
   限频与伪造字段都必须由服务端裁定。

## 3. 备选方案

1. **队伍持久化到 PostgreSQL。** 支持跨图/跨进程，但需要新表、迁移、状态机、
   清理任务和重连恢复；当前单 Room、单进程的规模收益不足，且会把“临时关系”
   变成“资产”。留到多地图/多进程需求出现时再评估。
2. **把队伍写进公开 Room State。** 客户端可以直接渲染，但所有玩家都能读到
   他人队伍的等级/HP；需要额外的可见性机制或重复的私有数据通道。
3. **队友各自再跑一次 `grantKillReward`。** 实现最快，但会重复掷掉落、重复发
   金币、重复推进任务，且经验取决于随机数，无法解释也无法对账。
4. **Room 内内存登记 + 私有消息 + 独立确定性分享事务（采纳）。** 复用现有
   CommandGuard、资产队列、幂等键与内容规则。

## 4. 决策

1. **队伍属于 Room，存在于内存。**
   - `PartyRegistry` 由 `WorldMapRoom` 持有；`partyId`、队长、成员顺序、待处理
     邀请与过期时间都在内存中。进程重启或 Room 销毁后队伍消失，客户端会收到
     `party.snapshot.party = null`（新 Room 加入时）。
   - 传送/最终离开/宽限期结束都会调用 `leave`；队长离开时按加入顺序提升下一
     名成员；最后一人离开时队伍解散。被移除成员发出的邀请一并失效。
   - 队员离开后，队长保留“1 人队伍”，不会自动解散——玩家可以继续邀请。
2. **名单只走私有消息。**
   - 新增 `party.snapshot`（服务端 → 单个客户端，`party` 可为 `null`）与
     `party.invite`（服务端 → 被邀请者）。
   - 加入世界后与队伍变化时，只向相关成员的连接发送快照；公开 Room State 不
     包含队伍字段。名单字段：`playerId`、`displayName`、`classId`、`level`、
     `hp/maxHp`、`alive`、`connected`、`leader`。
3. **邀请与成员规则由服务端裁定。**
   - Client → Server：`party.invite`（`targetPlayerId`）、`party.accept` /
     `party.decline`（`inviteId`）、`party.leave`；全部带
     `protocolVersion`、`commandId`、`clientSequence`。
   - 目标必须在线、在本 Room、与邀请者距离 ≤ `PARTY_INVITE_RANGE_TILES`
     （15 格）、且不在任何队伍中；同一目标只保留一条邀请，新邀请替换旧邀请，
     30 秒未处理自动失效；每个目标最多 4 名成员（内容 `rules.party.maxMembers`，
     线缆上限 8）。
   - 拒绝码：`PARTY_SELF`、`PARTY_TARGET_UNAVAILABLE`、`PARTY_TARGET_BUSY`、
     `PARTY_ALREADY_IN_PARTY`、`PARTY_FULL`、`PARTY_INVITE_EXPIRED`、
     `PARTY_NOT_IN_PARTY`。队伍命令走与资产命令相同的 `CommandGuard`
     （协议、重复 id、序号、限频），但同步执行，不进入资产队列。
   - 由他人伪造的 `party.accept` 不能取消原邀请（验证时只比较、不删除）。
4. **共享击杀经验是独立的确定性事务。**
   - 内容 `rules.party = { maxMembers, assistSharePermille, assistRangeTiles }`
     为可选 section；缺失时队伍仍可用，默认 4 人、不共享经验、12 格。
   - 击杀者照常获得完整掷骰奖励（经验、金币、掉落、任务进度）。对同队且
     存活、在线、距离怪物 ≤ `assistRangeTiles` 的其他成员，各自在击杀者奖励
     之后排入资产队列，执行 `grantPartyKillExperience`：
     - 经验 = `floor(怪物基础经验 × assistSharePermille / 1000)`，不消耗 RNG，
       因此重试不会改变数值；≤0 时不写事务。
     - 幂等键 `party_kill:<击杀引用>:<角色 id>`；`asset_commands.kind` 增加
       `party_kill_reward`。
     - 可升级、按升级回满 HP/MP；金币、掉落与任务进度不共享。
   - 队友的贡献不按伤害计算：站在范围内、同队且存活即分享，规则简单、可解释。
5. **不做的事（v1）。**
   - 队伍聊天、掉落/金币分配、队长移交按钮、踢人、跨地图队伍、离线保留、
     好友/公会。跨图队伍与队伍聊天需要新的频道与持久状态，留到有真实需求时
     单独立项。

## 5. 后果

正面：

- 玩家第一次有了“合作目标”：组队后打怪，双方都能成长；名单能看见队友的 HP
  与在线状态，便于协作与撤离。
- 没有新增数据库表或迁移；经验分享是内容数值，运营可在内容工作台调整后发布。
- 共享经验不经过随机数、不重复掉落、不重复推进任务，资产不变量可继续校验。
- 队伍名单不进入公开状态，陌生人无法读取他人队伍信息。

负面 / 风险：

- **经验膨胀**：每名队友额外获得怪物基础经验的 50%，4 人满队最多额外 150%。
  通过 `assistSharePermille` 与 `assistRangeTiles` 内容化控制；当前适用 4 人。
- **掉落共享后的归属**：窗口内队友可捡，但物品仍只有一个实例，由先拾取者
  获得；没有分配规则或队长分配，冲突时按先到先得（见 §7）。
- **进程崩溃丢队伍**：与 Room 内战斗状态一致，属于可接受损失；客户端会恢复
  为“未组队”。
- **1 人队伍**：最后一名队友离开后队长仍在队伍中，需要手动离队或解散；当前
  没有自动解散计时器，UI 显示 1/4。
- **没有队伍频道**：协作沟通仍依赖地图频道；跨图组队不可用。
- **经验仍无流水**（TD-DATA-11）：共享经验与击杀/任务经验一样只更新
  `characters.exp` 与 `asset_commands` 幂等行。

## 6. 验证

- 契约测试：名单上限、未知字段拒绝、命令元数据、邀请过期字段。
- `PartyRegistry` 单元测试：创建时机、仅受邀者可接受/拒绝、邀请替换与过期、
  满队/已组队拒绝、队长提升、解散、邀请清理。
- 应用集成（真实 PostgreSQL）：分享只发一次、独立角色不串账、升级回满、
  分享为 0 时不写库。
- 服务端集成（真实 PostgreSQL + Colyseus）：邀请/接受/拒绝/离开、名单同步、
  击杀后队友经验 +6、超出范围队友为 0、掉落归属仍只属于击杀者、伪造邀请被拒。
- 浏览器 E2E：两名玩家在真实 UI 中组队、离队、再组队、最后通过传送验证队伍
  随地图结束；证据 `docs/phase-reports/alpha-02/party/`。
- 资产不变量与容量回归按切片门禁执行。

## 7. 补充（2026-11-27）：队伍共享击杀掉落归属

首版只共享经验，掉落仍只归击杀者；试玩反馈指出“队友看得到却捡不起来，而
30 秒后路人反而能捡”不合理。补充规则：

- 归属窗口内，击杀者与**击杀者所在队伍**的成员都可以拾取该掉落；窗口过后
  任何人仍可拾取。
- 队伍成员由 Room 在拾取命令中传入（`PickupInput.partyMemberIds`，来自
  `PartyRegistry`），资产事务只校验“归属者在这个集合内”；`game-application`
  不依赖社交状态，也不新增物品行或复制掉落。
- 拾取距离（1.5 格）、幂等命令与竞态处理不变；窗口内离开队伍的成员不再享有
  共享资格，以拾取时的队伍为准。
- 队伍仍在传送时结束（TD-SRV-11 不变）；跨图共享掉落不在本次范围内。
