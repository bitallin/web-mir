# ADR-038：内容驱动的每日任务与周期键

- 状态：Accepted
- 日期：2026-11-27
- 阶段：Alpha 0.3 S3（每日任务与留存循环）
- 关联：ADR-022（内容发布）、ADR-034（内容驱动任务链与事务进度）、
  ADR-035（击杀奖励事务与队伍共享）、TD-DATA-12（每日历史行清理）

## 1. 背景

Alpha 0.2 S4-G 交付了三步主城任务链，Alpha 0.3 的主题是“玩家为什么每天
回来”。一次性任务链完成后没有新的目标；路线图的 Alpha 0.3 明确要求
“10–15 步主线 + 5 个日常/循环任务”。本轮先交付循环任务的基础机制：
内容描述日常任务，服务端按区服的“一天”重置，玩家每天可以重新接取与交付。

## 2. 问题

1. **现有任务表无法重复接取**：`character_quests` 上有
   `unique(character_id, quest_id)`，交付后 `status = 'claimed'` 永远保留。
   直接重置会丢失历史，也容易在并发下重复发奖。
2. **“一天”必须由区服定义**：不能用浏览器本地时间（玩家可改时钟），也不能
   只用宿主机本地时区（部署环境与玩家期望不一致）。所有客户端与服务端必须
   对同一个重置边界达成一致。
3. **进度与奖励不能另开链路**：任务进度仍在击杀奖励事务内推进，交付仍在
   单事务内发经验/金币/物品；日常不能引入第二套发奖路径。
4. **在线玩家跨过重置点**：玩家可能正在线，重置后必须看到日常重新可接取，
   而不是等到重进游戏。
5. **兼容性**：旧 Release 不含日常字段，历史一次性任务与已领取记录必须
   完全不受影响。

## 3. 备选方案

1. **交付时删除/重置任务行**：实现最短，但丢失历史；重置与交付如果不在
   同一把锁内，可能重复发奖；运营无法追溯。
2. **独立 `character_daily_quests` 表**：语义清晰，但查询、视图合并、接取/
   交付/击杀进度都要维护两条路径，且与一次性任务共用同一个 UI 与命令。
3. **周期键行（采纳）**：在现有表上增加 `period_key`，唯一约束变为
   `(character_id, quest_id, period_key)`；一次性任务使用空字符串，日常使用
   `YYYY-MM-DD`。每个周期是独立一行，历史自然保留，当前周期由纯函数计算。
4. **客户端判定重置**：拒绝。客户端时钟不可信，也不应参与任何权威状态。

## 4. 决策

1. **内容**
   - `QuestContent.repeat: 'daily'`，与任务目标一样是封闭白名单；新增循环
     类型需要代码发布。
   - 日常任务不能设置前置任务，也不能作为一次性任务的前置（内容校验报错）。
   - 新增 `rules.dailyReset = { hour, utcOffsetMinutes }`，描述区服本地重置
     时刻；发布含日常任务的内容但没有该规则时校验失败。
   - 基线内容：05:00（UTC+08:00）重置；两个守卫日常（5 只史莱姆 / 6 只
     森林狼）。
2. **持久化（迁移 0009）**
   - `character_quests` 增加 `period_key text NOT NULL DEFAULT ''`。
   - 旧唯一索引替换为
     `character_quests_character_quest_period_unique(character_id, quest_id, period_key)`。
   - 一次性任务恒为 `''`；日常每个周期一行。旧行保留为历史。
3. **领域（纯函数）**
   - `dailyPeriodKey(now, rule)` 与 `nextDailyResetAt(now, rule)`：把时间戳
     平移到区服本地时区后按重置小时划分日期，不依赖宿主机时区。
   - 视图解析时，日常记录若 `periodKey` 不等于当前周期则视为“不存在”：
     已领取的昨日日常重新显示为可接取，进度归零；一次性任务不受影响。
   - 击杀推进同样拒绝旧周期记录，避免跨日补记。
4. **应用事务**
   - `acceptQuest` / `claimQuest` 由注入时钟计算周期键，按
     `(character, quest, period)` 查询与写入；同一周期内重复接取/交付返回
     既有拒绝码。
   - `advanceQuestsOnKill` 只读取“一次性 + 当前周期日常”的记录，仍在击杀
     奖励事务内推进。
5. **服务端**
   - Room 每 30 秒检查一次周期键；跨过重置点时向所有会话重发任务快照并发
     一条系统公告。快照完全由内存记录与当前时间计算，不需要数据库读取。
   - 视图新增可选 `repeat` 与 `nextResetAt`（epoch 毫秒）；`nextResetAt` 由
     服务端计算，客户端只按玩家本地时钟格式化显示。
6. **客户端**
   - 任务面板显示「日常」标签与重置时刻；已交付显示「今日已完成」；追踪器
     同样带日常标记。

## 5. 后果

- **正向**：重置是纯函数，可用注入时钟做确定性测试；历史保留；接取/交付
  仍走既有资产命令、幂等键与行锁；一次性任务、旧 Release 与旧记录零改动；
  不需要定时清理或后台任务。
- **成本**：每个日常每天新增一行，需要后续清理策略（TD-DATA-12）；重置
  边界依赖宿主机时钟，多进程部署要求 NTP 同步；在线重置最多延迟一个 30 秒
  扫描周期；UI 只有静态重置时刻，没有倒计时。
- **非目标**：周常/赛季循环、击杀以外的日常目标、连续签到、按玩家时区
  的重置、日常接取提醒。

## 6. 验证

- 单元：重置边界前后一分钟的周期键、下一重置时间、旧周期记录在视图中
  失效、击杀不推进旧周期记录。
- 内容：日常缺少重置规则、日常带前置、一次性任务以日常为前置均被拒绝；
  基线内容校验 0 issue。
- 应用集成（真实 PostgreSQL）：同日重复接取/交付被拒绝；交付后跨日重新
  接取；旧周期进度不带到新周期；交付奖励只发一次。
- 服务端集成：任务快照带 `repeat: 'daily'` 与未来的 `nextResetAt`。
- 浏览器 E2E：守卫处接受日常 → 击杀 5 只史莱姆 → 交付 → 面板显示
  「今日已完成」且追踪器清空。
- 容量：50 人 × 2 分钟 tick p95 5.11ms、0 资产失败。
