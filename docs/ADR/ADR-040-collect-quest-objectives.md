# ADR-040：收集类任务目标与交物交付

- 状态：Accepted
- 日期：2026-11-27
- 阶段：Alpha 0.3 S3-D1（任务目标类型扩展）
- 关联：ADR-020（资产事务）、ADR-034（内容驱动任务链）、ADR-038（每日任务）、
  ADR-039（一键任务导航）、EL-004（内容 checksum 兼容）

## 1. 背景

十步主线与两个日常全部是“击杀 N 只怪物”。玩家已经熟悉战斗与一键导航，
但任务只有一种动词，材料除了卖店没有别的用途。S3-D 计划把任务目标扩展为
收集/到达，本切片先交付收集（交物）目标，到达目标留作 S3-D2。

## 2. 问题

1. **进度从哪里来**：击杀有明确的战斗事件；收集没有。可以选择“拾取时记进度”
   或“看背包当前数量”。
2. **物品必须被消耗**：交物任务的意义是把材料交出去；不能只在领取奖励时
   检查数量而不扣物品，否则同一批材料可以反复交付（每日任务尤其危险）。
3. **资产正确性**：扣物品与发奖励必须在同一事务；并发出售/交付不能重复使用
   同一件物品；失败必须整体回滚。
4. **视图与数据库状态**：任务面板要显示“已收集 2/3”与“可交付”，但收集进度
   随背包实时变化，不应在每次拾取时写一行任务进度。
5. **不能变成金币水龙头**：如果每日任务要求商店可购买的物品，玩家可以花金币
   买物品换金币奖励，形成套利。
6. **导航与交付**：一键流程要能把玩家带到会掉落目标物品的怪物身边；背包凑够
   后停止自动战斗，返回发布者交付。
7. **历史内容兼容**：旧 Release 只有击杀目标，新增目标类型不能改变它们的
   checksum 或校验结果。

## 3. 备选方案

1. **拾取时记录进度，交付时不扣物品**：实现最接近击杀目标，但玩家可以在交付
   前把材料卖掉，进度仍显示完成；每日任务还能用同一批材料反复交付。
2. **拾取时记录进度 + 交付时扣物品**：能解决重复交付，但需要在拾取、购买、
   任务奖励、商店回收等所有获取路径上挂钩；卖掉材料后进度与背包不一致，
   还要额外处理“进度倒退”。
3. **背包即进度 + 交付时扣物品（采纳）**：视图直接从背包汇总数量；背包够数
   即显示可交付；领取事务在行锁内扣除物品、标记完成/已领取并发放奖励。
   没有新的写入路径，也不会出现进度与背包不一致。

## 4. 决策

1. **内容契约**：`questObjectiveSchema` 增加闭集分支
   `{ kind: 'collect', templateId, count }`；视图增加
   `{ kind: 'collect', templateId, itemName, count }`。新类型需要代码发布
   （与技法效果、任务目标一样是白名单）。
2. **进度来源**：`questViewFor` 接收服务端内存中的背包汇总
   （`templateId → 数量`，只统计背包，不含装备）。收集任务在记录为 `active`
   时，`progress = min(持有数量, count)`；持有数量达到要求即把视图状态显示为
   `completed`。数据库行在领取前保持 `active`，不因拾取而写进度。
3. **领取事务**（`AssetService.claimQuest`）：
   - 先锁角色行（既有顺序）；
   - 以 `FOR UPDATE` 锁住该模板的背包堆叠，按槽位从早到晚扣除；
   - 数量不足返回 `QUEST_ITEMS_MISSING`，整个事务回滚（幂等命令行也回滚）；
   - 足够时把任务行 `active → completed → claimed`（同事务内两步），
     再发放经验/金币/物品；任何一步失败都整体回滚，物品不会凭空消失。
4. **视图刷新**：Room 在每次资产命令提交后，如果该会话存在进行中的收集任务，
   重发一次任务快照；不新增 tick 内数据库读取，也不在拾取路径写任务进度。
5. **导航与交付**：
   - `hunt` 对收集任务选择“战利品表里掉落该物品的怪物”，复用既有自动攻击；
   - 背包凑够后导航以 `completed` 停止，不继续抢怪；
   - `return` 的“已完成”判定把“背包已够数”的活动记录视为完成；
   - 到达后仍由客户端发送既有 `quest.claim`，服务器校验距离、数量与幂等。
6. **内容校验**：
   - 目标物品必须存在；
   - 只能是材料或消耗品（不能是装备，避免交出唯一武器）；
   - 每日收集任务不能要求商店可购买的物品（避免金币套利）；
   - 同一任务的目标物品不能同时是奖励物品；
   - 物品既无掉落也无商店来源时给出警告。
7. **允许预先持有**：玩家在接取前就拥有物品时，接取后立刻显示可交付。这是
   “带物品来”的原型，不视为漏洞；每日任务的物品消耗与重置仍按周期键隔离。

## 5. 后果

- 无数据库迁移：`character_quests.progress` 继续存在，收集任务在领取时写入
  `count` 作为历史记录；唯一约束、CHECK 与周期键不变。
- 历史 Release 不含收集目标，schema 的加法扩展不影响其解析与 checksum。
- 物品被消耗时不写金币账本（没有金币变化）；交付的审计由任务行状态、
  `asset_commands` 幂等行与物品行删除共同构成。
- 每日收集是物品消耗端，产出经验与金币；平衡由内容数值控制，校验只阻止
  可直接套利的配置。
- 导航对收集任务会同时把玩家带向多个掉落来源；目标选择仍是“最近的可见怪”。
- 未覆盖：到达目标（S3-D2）、组队共享收集进度、任务放弃与任务日志。
