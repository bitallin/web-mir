# ADR-049：行会目录与入会申请

- 状态：Accepted
- 日期：2026-11-28
- 阶段：Alpha 0.3 S5-B 行会发现与入会申请
- 关联：ADR-048（行会持久化、权限与频道）、ADR-045（好友关系）、
  ADR-046（在线目录）、TD-CLI-25

## 1. 背景

S5-A 交付了行会最小闭环，但新玩家只能被在线会长“看见并邀请”。这要求双方
同时在线且彼此可见，行会没有发现入口，TD-CLI-25 也明确记录了“无申请”这一
缺口。

试玩反馈直接指出：玩家点击「行会」时应该看到当前区服的所有行会，并能申请
入会。这个需求把行会从“熟人邀请制”扩展为“可发现、可申请”的社交结构，同时
不能泄露成员名单、在线状态或申请内容。

## 2. 问题

1. **发现**：无行会玩家需要一个入口看到本区服存在哪些行会，而不是只能等邀请。
2. **申请**：玩家应能向行会提交入会申请；会长需要一个处理入口。
3. **持久性**：申请在会长离线时提交、会长上线后处理，不能只存在内存里。
4. **隐私**：目录可以公开行会名、会长名与人数，但成员名单、在线状态与申请
   列表必须只对行会内部可见；申请只对会长可见。
5. **并发**：多个玩家同时申请，或会长接受时行会已满、申请人已加入其他行会，
   都不能产生超员、双行会或无提示失败。
6. **兼容**：旧客户端、旧快照与协议版本不应被破坏；目录与申请是加法字段。

## 3. 备选方案

1. **只做进程内申请**：实现最快，但会长离线即丢，无法满足“上线后处理”；拒绝。
2. **申请写入 Redis**：当前单进程且未启用 Redis，引入新的持久事实来源；拒绝。
3. **公开完整行会名单**：能看到哪些人在哪个行会，泄露社交关系；拒绝。
4. **每个玩家只能申请一个行会**：规则简单但会阻塞玩家比较多个行会；且
   “申请后反悔”没有入口；本切片允许多个申请，接受其中一个时清理其余。
5. **申请长期不清理**：会长列表会无限增长；本切片在接受/拒绝/加入/创建行会
   时删除相关申请，并把列表上限控制在 100 条；TTL 留作后续（TD-SRV-18）。
6. **采纳：持久化目录摘要 + 持久化多行会申请 + 会长私有申请列表 + 接受时
   事务加入并清理申请**。

## 4. 决策

### 4.1 目录公开范围

- 新增 `guild.directory` 命令与 `guild.directory` 消息；返回当前角色所在
  区服的行会摘要（最多 `GUILD_DIRECTORY_MAX = 50` 条）。
- 每条摘要只包含：行会 id、名称、会长显示名、成员数、成员上限、当前玩家是否
  已申请。**不包含**成员名单、在线状态、申请列表或角色 id。
- 目录按成员数降序、创建时间升序排列；所有行会（含已满）都可见，已满时申请
  按钮禁用。
- 目录只在玩家未加入行会时由客户端请求；服务端不限制已入会玩家读取公开
  摘要，但 UI 不提供入口。

### 4.2 申请模型

- 新表 `guild_applications`：`(guild_id, character_id)` 唯一、`created_at`；
  角色或行会删除时级联清理。
- 一个角色可以同时向多个行会申请；同一行会的重复申请是幂等成功，不新增行。
- 申请前置：角色未加入任何行会、与行会同区服、行会未满。行会已满返回
  `GUILD_FULL`，申请人已有行会返回 `GUILD_ALREADY_IN_GUILD`。
- 申请不设 TTL；接受、拒绝、加入其他行会或自己创建行会时删除相关申请。
  会长申请列表上限 `GUILD_APPLICATION_LIST_MAX = 100`，按申请时间升序。
- 申请只对会长可见：`guild.snapshot` 增加 `applications` 字段（默认空数组），
  仅当请求者是会长时填充。

### 4.3 处理申请

- 只有会长可以接受或拒绝；目标申请必须属于本行会。
- 接受在一个事务内：锁行会行 → 校验申请人未加入任何行会 → 校验未满 →
  插入成员 → 删除申请人的全部申请。申请人已在其他行会或行会已满时整体回滚
  并返回可区分拒绝码。
- 拒绝删除该申请；重复处理返回 `GUILD_APPLICATION_NOT_FOUND`。
- 申请成功时向在线会长推送 `guild.refresh` 与提示；会长离线时申请保留，
  上线后的快照携带申请。接受/拒绝后向申请人推送提示；接受后申请人所在 Room
  通过 `guild.refresh` 收到新名单。

### 4.4 协议与客户端

- 新命令：`guild.directory`、`guild.apply`、`guild.apply.accept`、
  `guild.apply.decline`。
- 新消息：`guild.directory`；`guild.snapshot` 增加默认空的 `applications`。
- 拒绝码新增 `GUILD_APPLICATION_NOT_FOUND`；其余复用既有行会拒绝码。
- 客户端未入会时显示“行会列表”和创建表单；每行显示会长、人数与申请状态；
  会长在行会面板看到“入会申请”与接受/拒绝。申请成功后目录行显示“申请中”。
- 已入会玩家不显示目录；离会/解散后重新请求目录。

## 5. 后果

- 正向：行会可被发现、可申请，解决了“必须同时在线且互相可见”的冷启动问题；
  申请持久化，会长离线也能处理；目录不泄露成员关系。
- 代价：新增一张表与四个命令；目录查询需要聚合成员数与会长名；申请没有 TTL，
  长期未处理会累积（列表已限 100，删除策略见 TD-SRV-18）。
- 未决：申请备注、申请数量限制、申请过期、行会搜索/分页、副会长处理申请、
  行会公告与审批流。

## 6. 验证

- 契约：目录摘要、空申请默认值、四个命令与申请视图的边界。
- 应用集成（真实 PostgreSQL）：多行会申请、幂等重复申请、满员/已有行会拒绝、
  接受后清理全部申请、拒绝与重复处理、并发接受不超员。
- 服务端集成（真实 Room）：目录含会长/人数/是否已申请；跨图申请；会长快照
  含申请；接受后双方名单与申请清理；非会长拒绝；满员拒绝。
- 浏览器 E2E：无行会玩家打开面板看到目录并申请，会长看到申请并接受，双方
  名单变为两人；拒绝路径与“申请中”状态。
- 门禁：lint/typecheck/全量测试/构建、50 人 × 2 分钟容量 sanity 与资产不变量。
