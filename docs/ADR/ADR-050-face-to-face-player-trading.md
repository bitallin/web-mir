# ADR-050：面对面玩家交易

- 状态：Accepted
- 日期：2026-11-28
- 阶段：Alpha 0.3 S5-C 玩家交易最小版
- 关联：ADR-020（资产事务与幂等）、ADR-026（商店金币闭环）、
  ADR-041（怪物归属与拾取）、ADR-048（行会频道与私有消息）、
  TD-ECO-01、TD-DATA-11

## 1. 背景

Alpha 0.3 的路线把“玩家间经济”列为核心玩法，当前只有 NPC 商店：产出金币
只能回到商店，玩家之间无法直接把装备、材料或药水转给朋友。试玩与路线都把
“面对面交易”列为下一片。

交易是经济系统里最容易被复制资产的路径。它必须在服务端完成、必须在一个
数据库事务里同时移动双方的物品与金币、必须幂等，并且不能让任何一方在对方
确认后单方面撤回。

## 2. 问题

1. **双确认**：双方各自确认报价后才能结算；任何一方修改报价，双方都必须
   重新确认。
2. **一致性**：物品和金币要么同时到达双方，要么都不动；不能出现一方失去物品
   而另一方没收到。
3. **并发**：结算期间双方可能同时在拾取、买卖或使用物品；交易不能基于过期
   的客户端快照。
4. **防复制**：同一笔交易重复提交、断线重连、服务端重启都不能让资产结算两次。
5. **范围**：交易应是面对面的行为，必须同图、近距、双方存活；不允许远程
   交易或跨图交易。
6. **兼容**：交易是加法协议；旧客户端、旧内容 Release、协议版本不受影响。

## 3. 备选方案

1. **把交易会话持久化到 PostgreSQL**：可以在进程重启后恢复交易，但交易是
   短生命周期的交互状态，持久化会引入会话表、过期清理与恢复语义；当前单
   进程且队伍/行会邀请也采用进程内状态，暂不采用。
2. **交易走邮件/拍卖行**：异步交易价值更高，但需要挂单、搜索、税率、过期与
   经济防护，属于后续切片；本片先做最基础的面对面交易。
3. **客户端自行交换物品 ID**：违反服务端权威；拒绝。
4. **允许部分数量交易**：更灵活，但需要拆分堆叠、重新分配槽位与客户端
   数量输入；本片先以“整堆”交易验证闭环，部分数量留作后续。
5. **采纳：Room 内进程级交易会话 + 单一 PostgreSQL 结算事务 + 双方锁定后
   自动结算**。

## 4. 决策

### 4.1 交易范围与生命周期

- 双方必须**在同一条地图 Room** 内，且彼此距离 ≤ `TRADE_RANGE_TILES = 3`
  格；邀请、接受、修改报价与锁定都会重新校验。
- 双方必须存活；任一方死亡、离开地图、过图或断线时，交易立即取消并通知
  另一方。
- 邀请 30 秒过期（`TRADE_INVITE_TTL_MS`）；同一时间一个角色只能参与一笔
  交易，可以有多个未处理邀请，但接受时会再次检查双方是否已被占用。
- 交易会话只存在于当前 Room 内存中：服务端重启会丢失进行中的交易，但已提交
  的结算不会丢。与 TD-SRV-11/12/15/16 同类，记录为 TD-SRV-19。

### 4.2 报价模型

- 每一方最多提供 `TRADE_MAX_ITEM_STACKS = 8` 个**完整物品堆叠**；本片不支持
  拆分数量。金币范围 0–`TRADE_MAX_GOLD = 1_000_000`。
- 只有背包中的物品可交易；已装备物品不在背包视图中，因此不可直接交易。
- 与商店的“绑定”语义一致：`sellPrice` 不存在或为 0 的物品不可交易（新手
  武器），避免玩家把唯一武器转走后无法战斗。该规则由
  `isTradeableItem` 统一实现，服务端在报价与结算时都校验。
- 任何一方修改报价（增减物品或改金币）都会清除双方的锁定状态。
- 双方都锁定后进入 `settling`，结算失败（背包满、金币不足、物品已变化、
  距离过远）则回到 `open` 并解锁双方，由玩家调整；离开/死亡/断线则取消。

### 4.3 结算事务

`AssetService.settleTrade` 在一个 PostgreSQL 事务内完成：

1. 按角色 UUID 升序对双方角色行 `FOR UPDATE`，与既有资产命令使用同一把行锁，
   避免交叉交易死锁。
2. 对双方分别写入 `asset_commands`（kind `trade_settle`，幂等键包含
   `tradeId`）。任一方已有该键说明交易已提交，返回幂等结果，不再移动资产。
3. 锁定双方报价的物品行，重新校验归属、容器为背包、数量与可交易性；锁定
   双方钱包并校验金币充足。
4. 删除双方报价的物品行，再按“先移除、后放入”的模拟结果放入对方背包：
   可堆叠物品优先合并，否则使用空槽；任一背包放不下则整体回滚。
5. 同事务更新双方钱包并写入两条 `currency_ledger`（`trade_settle`，参考
   `tradeId`）；双方余额与流水同事务提交。
6. 返回双方新的 `InventorySnapshot`，提交成功后才向客户端确认。

物品实例在交易后使用新的行 ID 是允许的：交易消耗旧实例并在对方背包创建新
实例，审计以 `tradeId`、账本与资产命令为线索，不依赖实例 ID 的连续性。

### 4.4 协议与隐私

- 新命令：`trade.invite`、`trade.accept`、`trade.decline`、`trade.offer`、
  `trade.lock`、`trade.cancel`。
- 新消息：`trade.invite`、`trade.state`。两者都只发给参与者本人，不进入公开
  Room State，第三方无法读取对方报价或交易关系。
- `itemView` 增加可选 `tradeable`，由服务端按内容规则计算；客户端据此禁用
  不可交易物品的“加入交易”按钮，服务端仍独立校验。
- 拒绝码新增 `TRADE_*` 系列；协议版本不变，旧命令与消息不受影响。

### 4.5 客户端

- 附近玩家行增加「交易」；收到邀请时显示与组队/行会一致的邀请横幅。
- 交易面板右侧停靠，显示双方报价、各自锁定状态与金币；本方面板列出背包中
  可交易物品，点击整堆加入/移除，金币输入在失焦或回车时提交。
- 双方锁定后显示“结算中”，成功后提示成交并刷新背包；失败时保持面板打开并
  显示原因。
- 面板不遮挡玩家、技能坞与聊天；与商店、背包、任务、好友、行会面板互斥。

## 5. 后果

- 正向：玩家之间可以直接交换装备、材料与金币，形成“打到的多余装备可以给
  队友”的多人价值；结算原子、幂等、可审计。
- 代价：交易会话不跨进程/重启（TD-SRV-19）；只支持整堆物品，没有数量拆分；
  没有税率、交易记录查询、黑名单或防诈骗提示（TD-ECO-06）；交易面板新增
  一段 UI 与 E2E 维护成本。
- 未决：拍卖行/摆摊、交易税、交易历史与回溯、部分数量、跨图交易、交易中
  聊天、物品绑定系统。

## 6. 验证

- 契约：交易状态、报价命令边界、邀请视图、非法组合（超 8 堆、负金币、
  重复物品）。
- 应用集成（真实 PostgreSQL）：双方物品与金币互换、背包满回滚、报价物品
  已被出售时回滚、金币不足回滚、重复 `tradeId` 幂等、账本与钱包一致。
- 服务端集成（真实 Room）：邀请/接受/拒绝、同图距离限制、双方锁定后结算、
  修改报价解锁、离开/死亡取消、非参与者拒绝、公开 State 不含交易字段。
- 浏览器 E2E：两名玩家近距离交易一件材料与金币，双方背包与金币正确变化；
  邀请拒绝路径与锁定状态可见。
- 门禁：lint/typecheck/全量测试/构建、50 人 × 2 分钟容量 sanity、资产不变量。
