# ADR-036：队伍提升为进程级服务，过图保留

- 状态：Accepted
- 日期：2026-11-27
- 阶段：Alpha 0.3 S1 补充（社交基础）
- 关联：ADR-003（每地图固定 Room）、ADR-035（组队与共享击杀经验）、
  TD-SRV-11（队伍仅内存且以 Room 为边界）、TD-SRV-03（资产单队列）

## 1. 背景

ADR-035 把队伍放在地图 Room 的内存里，换取“不引入持久社交状态”；代价是
**过图即散队**（传送是离开旧 Room、加入新 Room）。试玩反馈把它视为缺陷：
两人在主城组队后一起去野外，队伍在传送瞬间消失，需要重新邀请。

本 ADR 把队伍提升到游戏服务器进程级，让队伍跨地图保留；仍然不做跨进程、
重启保留或队伍聊天。

## 2. 问题

1. **成员分布在不同 Room**：名单需要跨 Room 汇总（等级、HP、在线状态），
   但 Room 之间没有现成的数据通道。
2. **快照与邀请的投递**：成员在另一张地图时，名单更新和组队邀请必须送到
   对应的 Room，而不是当前 Room。
3. **传送的空窗**：传送期间角色不在任何 Room；队伍不能因此散掉，但名单要
   能表达“暂时不可见”。
4. **生命周期**：真正离开世界（主动退出、宽限期结束、踢下线、封禁）必须
   移出队伍；Room 销毁不等于队员离队（队员可能已经传送到别处）。
5. **规则边界**：共享经验和共享掉落仍然要求同图、近距离；跨图队友只能查看
   名单，不能远程吃经验或拾取。
6. **进程与内容配置**：队伍上限来自内容规则，但队伍表是进程级；一个进程内
   所有地图必须使用同一个上限。

## 3. 备选方案

1. **把队伍持久化到 PostgreSQL。** 支持跨进程与重启保留，但需要新表、迁移、
   清理任务与断线重连语义；当前单进程、单区服的规模收益不足。若未来多进程
   路由或重启保留成为需求，再单独评估。
2. **每个 Room 保留队伍，但传送时把队伍交接给目标 Room。** 需要 Room 之间的
   注册与消息通道，复杂度接近进程级服务，却只能解决两人同图交接。
3. **进程级 PartyService（采纳）。** 一个进程内所有 Room 共享队伍表、邀请与
   在线状态；Room 负责上报宿主状态与投递消息。

## 4. 决策

1. **进程级 `PartyService`。**
   - `createGameServer` 创建一个实例，注入每个 `WorldMapRoom`；Room 只保留
     会话、战斗与地图状态。
   - 队伍表、邀请与过期、队长提升、解散逻辑复用既有 `PartyRegistry`
     （ADR-035 的状态机不变），服务在其上增加在线状态与消息路由。
2. **在线状态（presence）由宿主 Room 上报。**
   - `PartyMemberPresence`：角色 id、显示名、职业、等级、HP/最大 HP、存活、
     在线、所在 Room。
   - 进入世界时立即上报；宿主 Room 每秒刷新一次（HP、存活、在线）；传送时
     `markOffline` 保留队伍席位并把状态标为离线。
   - 角色最终离开世界（主动退出、宽限结束、踢下线）调用 `removePlayer`，
     同时移出队伍与在线状态；Room 销毁只清理自己的会话。
3. **名单只走私有快照，按宿主 Room 路由。**
   - Room 向服务注册一个端口：`sendInvite`（投递给本 Room 的某个角色）与
     `refresh`（重发这些角色的名单快照）。
   - 名单由 presence 构建，因此跨图成员以 1 秒粒度更新；成员变化（加入、
     离开、队长变化）立即刷新所有相关成员的 Room。
   - 组队邀请由服务路由到被邀请者当前所在的 Room；若被邀请者正在传送空窗，
     邀请保留，进入新 Room 后补发。
4. **不改变同图规则。**
   - 共享击杀经验、共享掉落拾取仍要求在同一 Room 且满足距离；跨图成员不在
     本 Room 的会话/角色表中，自然不参与。
   - 邀请仍在当前视野内发起（15 格）；接受可以在过图后完成，因为邀请记录在
     服务里。
5. **队伍上限来自内容，进程内统一。**
   - 服务在内容 Store 启动后读取 `rules.party.maxMembers`；修改该值需要重启
     游戏服务器，不会影响已存在的队伍。名单快照中的 `maxMembers` 使用同一值。
6. **不做的事。**
   - 不持久化队伍，进程重启/崩溃后队伍消失。
   - 不做跨进程队伍、队伍聊天、掉落分配规则、队长移交或按名字邀请。
   - 名单暂不显示成员所在地图（可作为后续 UI 补充）。

## 5. 后果

正面：

- 过图不再散队，玩家可以“先组队、再一起出城”；传送空窗期名单仍保留成员。
- 队伍状态只有一份，名单、邀请与在线状态在进程内一致；Room 仍然只做适配。
- 同图共享规则不变，跨图成员不会被远程发经验或掉落，经济边界清晰。

负面 / 风险：

- **进程重启丢队伍**：与 ADR-035 相同，属于可接受损失；多人/多进程部署前需
  要持久化或共享存储。
- **名单刷新频率**：每个队伍成员每秒收到一次快照（最多 8 人），50 人满员时
  约 50 条小消息/秒；当前可接受，队伍规模或人数上升时再按需节流。
- **跨图不可见**：名单只显示在线状态，不显示成员在哪张地图，也没有“点击
  跟随/传送”入口。
- **内容上限需重启**：`rules.party.maxMembers` 的修改不会热更新到进程级队伍表。
- **邀请投递依赖在线状态**：角色在 Room 之间时无法立即收到邀请，进入新 Room
  后才补发；30 秒有效期不变。

## 6. 验证

- `PartyService` 单元测试：按宿主 Room 路由邀请、接受后刷新两个 Room、
  传送（离线保留席位、目的地恢复在线）、离队与离开世界的区别。
- 服务端集成（真实 PostgreSQL + Colyseus）：两人在主城组队 → 一人走到传送门
  过图 → 旧地图队友仍看到 2 人名单且过图者短暂离线 → 新地图恢复队伍与在线
  状态。
- 浏览器 E2E：两人组队、离队、再组队，一人过图后双方名单仍为 2 人，过图者
  恢复在线；证据 `docs/phase-reports/alpha-02/party/`。
- 容量与资产不变量沿用切片门禁；名单刷新在无队伍时不产生额外消息。
