# ADR-048：行会持久化、权限与行会频道

- 状态：Accepted
- 日期：2026-11-28
- 阶段：Alpha 0.3 S5-A 行会最小闭环
- 关联：ADR-035/036（组队与进程级服务）、ADR-044（队伍权限与聊天频道）、
  ADR-045（好友与持久关系）、ADR-046（在线目录与跨图投递）、ADR-047（最近
  同玩）、路线图 4.3“组队与社交”、TD-SRV-11/15

## 1. 背景

Alpha 0.3 已交付任务、首领、组队、好友、私聊与最近同玩。下一步计划明确
“行会先写 ADR”。行会是长期社交结构：它把一次组队关系变成稳定的身份、名单与
频道，也为后续行会活动、副本与排行榜提供归属。

当前队伍与好友已各自解决了一部分问题：队伍是进程内临时状态，好友是持久关系，
在线状态与跨图投递统一由 `PlayerDirectory` 负责。行会同时需要“持久归属”和
“在线名单”，必须明确哪些数据落库、哪些只是在线态。

## 2. 问题

1. **持久归属**：行会名、成员与职位必须在进程重启、过图与重新登录后保持一致；
   行会不能像队伍一样只存在于内存。
2. **权限**：谁可以创建、邀请、踢人与解散；会长离会时行会如何继续存在。
3. **唯一性**：一个角色只能属于一个行会；行会名必须在区服内唯一，且要避免
   全角/大小写造成的重名。
4. **邀请**：行会邀请需要跨地图；被邀请者可能离线、已在其他行会或行会已满。
5. **频道**：行会聊天必须只投递给在线成员，跨地图可读，不进入公开 Room State，
   也不写入数据库。
6. **隐私**：行会名单属于私有数据；其他玩家不能通过公开状态读取行会成员。
7. **兼容**：旧客户端、旧协议版本、旧内容与既有迁移不应被破坏。

## 3. 备选方案

1. **行会完全进程内**：实现最快，但重启即丢，和“长期社交结构”矛盾；拒绝。
2. **行会/成员写入公开 Room State**：任何客户端能读到别人的行会关系，泄露
   隐私；拒绝。
3. **行会与成员关系全部放进 `PlayerDirectory` 内存缓存**：避免数据库读取，
   但重启丢失且需要跨进程协调；当前单进程用不上，拒绝。
4. **行会创建收费（金币）**：能形成金币消耗端，但需要把行会事务接入资产事务、
   账本与幂等键，扩大本切片风险；本切片先以等级门槛限制刷会，收费留作经济
   切片（TD-ECO-05）。
5. **会长离会时禁止离会，必须先转让或解散**：规则清晰但操作成本高，容易出现
   “会长消失，行会僵死”；改为自动把会长交给最早加入的成员，最后一人离会时
   行会自动解散。
6. **采纳：PostgreSQL 持久化行会与成员 + 进程级邀请/在线投递 + 私有快照 +
   行会聊天频道**。

## 4. 决策

### 4.1 持久化模型

- 新增迁移：`guilds` 与 `guild_members`。
- `guilds`：`id`（UUIDv7）、`realm_id`（FK `realms`，`ON DELETE RESTRICT`）、
  `name`、`name_normalized`、`created_at`；`(realm_id, name_normalized)` 唯一。
- `guild_members`：复合主键 `(guild_id, character_id)`，`role`
  （`leader | member`）、`joined_at`；`character_id` 唯一，保证一人一行会；
  `guild_id` 建索引；每个行会最多一个 `leader` 的部分唯一索引。
- 行会名与角色名一样使用 NFKC + 去首尾空白 + 小写作为归一化键；显示名保留
  玩家输入的规范形式。长度 2–12，只允许字母、数字、汉字与下划线。
- 行会属于区服：邀请与加入都要求角色与行会同区服；跨区服的行会不在本切片
  范围。

### 4.2 权限与生命周期

- 创建：角色等级 ≥ 5、当前不属于任何行会、名称在区服内未被占用；创建者在
  同一事务内成为会长。本切片不收取金币（TD-ECO-05）。
- 邀请：只有会长可以邀请；目标必须在线、与行会同区服、不属于任何行会、
  行会未满。邀请 30 秒过期，同一目标只保留最新一条。
- 接受/拒绝：被邀请者只能处理发给自己的邀请；接受时在同一事务内锁定行会行、
  重新检查人数与“尚未加入行会”，再插入成员。
- 离会：普通成员直接删除成员行；会长离会时把会长交给 `joined_at` 最早的
  剩余成员；最后一名成员离会时删除行会。
- 踢人：只有会长可以踢出其他成员；会长不能踢自己（用离会/解散表达）。
- 解散：只有会长可以解散；删除行会行，成员行级联删除。
- 成员上限：`GUILD_MEMBER_LIMIT = 30`（契约常量）。后续内容化时再迁移到
  `rules.guild`；本切片不引入内容发布。

### 4.3 邀请与在线态

- 邀请记录保存在进程级 `GuildInviteRegistry`，与 `PartyService` 同层；
  记录包含行会、邀请人、目标与过期时间，不进入数据库。
- 邀请通过 `PlayerDirectory` 投递到目标所在 Room；目标过图期间无 Room 时
  投递失败，邀请仍在有效期内，重新进入地图后可继续处理。
- 行会名单的在线、等级、职业与存活状态在生成快照时从 presence 合并；数据库
  只保存归属与职位。进程重启后名单仍在，在线状态重新建立。

### 4.4 协议与频道

- 新增客户端消息：`guild.create`、`guild.invite`、`guild.accept`、
  `guild.decline`、`guild.leave`、`guild.kick`、`guild.disband`、`guild.list`。
- 新增服务端消息：`guild.snapshot`、`guild.invite`、`guild.presence`、
  `guild.refresh`。
- `chat.send` / `chat.message` 的 `channel` 增加 `guild`。省略频道仍是地图聊天；
  旧客户端行为不变，协议版本不升级。
- 行会聊天只投递给在线成员，复用既有过滤、限频、禁言与去重；不落库、不进入
  公开 Room State。成员在过图间隙可能漏掉消息，这是与队伍/私聊一致的取舍。
- 行会名单、邀请与在线变化只走私有消息；公开 `PlayerState` 不新增字段。

### 4.5 客户端

- 状态板新增「行会」入口；未加入行会时可输入名称创建并查看收到的邀请；已加入
  时显示行会名、会长、成员数与成员名单（在线状态、等级、职位）。
- 会长在附近玩家行看到「邀请入会」；成员行提供「踢出」；会长提供「解散」，
  所有成员提供「离会」。
- 聊天标题栏与发言频道增加「行会」，未加入行会时禁用；离会/解散/被踢后自动
  回到「附近」。
- 不提供全局行会搜索、加入申请、职位体系（副会长/成员审批）与公告；这些留作
  后续切片，避免本切片过大。

## 5. 后果

- 正向：行会归属在重启后保留；名单与频道形成稳定的多人回路；权限规则集中在
  服务端事务与命令门禁中；公开状态不泄露行会关系。
- 代价：新增两张表与一个迁移；行会命令增加异步数据库路径（不在 tick 内）；
  行会聊天每次发送需要一次成员查询（成员上限 30，当前量级可接受）。
- 未决：行会创建收费、行会等级/资金、公告、副会长、加入申请、行会活动与
  行会排行榜。行会邀请仍是进程内状态，重启后丢失（与 TD-SRV-15 同类）。

## 6. 验证

- 契约：名称、命令、快照、频道与拒绝码的解析与边界。
- 应用集成（真实 PostgreSQL）：创建/重名/等级门槛、邀请前置条件、加入人数
  上限、并发加入、离会转让、最后一人解散、踢人权限与解散。
- 服务端集成（真实 Room）：创建、跨图邀请、接受、名单在线状态、行会聊天
  跨图投递、非成员拒绝、离会/解散后的快照清理。
- 浏览器 E2E：两名真实浏览器玩家创建行会、邀请、接受、行会聊天、名单与离会。
- 验证：lint/typecheck/全量测试/构建；50 人 × 2 分钟容量 sanity 与资产不变量
  作为门禁。
