# Web Legend 演进日志

- 目的：记录**里程碑级**的产品与技术演进——为什么做、做了什么关键决策、结果
  如何、复盘出什么。它不是任务流水账。
- 与 `docs/WORKLOG.md` 的分工：WORKLOG 记录每次任务的命令、改动、测试输出与
  问题；EVOLUTION_LOG 只保留版本/里程碑层面的判断与反思，供未来会话快速理解
  “项目为什么是现在这个样子”。
- 与 ADR 的分工：ADR 固化不可默默更改的架构决策；本文记录决策发生的背景、
  结果与复盘，并链接对应 ADR。
- 规则：追加式，不覆盖历史；每条必须有代码、测试或运行证据；未验证的事项明确
  标注。

## 2026-11-25 Alpha 0.1：先让“完成”可被证明

**目标**：在进入新玩法前，关闭 MVP 审计发现的 8 项 P1，让 CI、E2E、容量与
资产正确性具备可复现证据。

**关键决策**

1. 自动攻击由服务端状态机驱动，客户端只提交一次锁定意图；冷却、射程、安全区
   仍由领域层裁定（ADR-025）。
2. 战斗事件按 AOI 与归属投递，治疗/复活只发给本人，公共公告仍全图。
3. E2E 使用专用数据库与端口；封禁/踢下线不再进入可重连宽限，重连重新校验
   账号状态。
4. Room 只做行为等价的第一阶段拆分（`SessionRegistry`、`CommandGuard`、
   `StateViewPublisher`），剩余编排明确为 TD-SRV-01b。

**结果**：8 项 P1 全部关闭；345 个测试、21 个浏览器 E2E、50 人 × 10 分钟
容量回归与恢复演练通过；资产不变量 0 违例。tick p95 10.25ms，略高于 10ms
目标，保留为 Alpha 0.2 性能项。

**反思**：正确之处是“先补证据再开发”，以及不把大重构和玩法放在同一批。
不足之处是容量目标被压线、远端 CI 仍未真实执行、人工试玩证据缺失。

## 2026-11-25 Alpha 0.2 S1：让金币第一次有用途

**目标**：关闭“金币只增不减、材料无价值、回城无意义”的 30 分钟体验断点。

**为什么把商店排在三职业之前**：职业差异是第二层问题；如果玩家没有补给与
装备决策，再多的技能也只是站桩输出。商店同时能验证内容价格、资产事务、
服务端权威、客户端面板与 E2E 全链路，是性价比最高的第一个纵向切片。

**关键决策**

1. 物品价格进入内容（可选 `buyPrice`/`sellPrice`），旧 Release 不使用默认值，
   避免 checksum 变化导致已发布内容失效（ADR-026）。
2. 买卖复用钱包、账本、资产命令与物品实例，不新增表；金币与物品同事务，
   命令幂等，并发扣款用条件更新。
3. NPC 交互由编译地图的 `role` 声明，服务端校验距离；客户端不提交价格、
   金币结果或最终位置。
4. 新角色 50 金币启动资金；初始职业武器绑定，避免新玩家卖掉唯一武器。
5. 资产命令统一改为先锁角色行再写幂等命令，消除外键共享锁造成的死锁。

**结果**：63 文件 362 测试、22 个浏览器 E2E、7 项资产不变量通过；商店 E2E
走通“50 金币 → 买药 35 → 卖药 40 → 离开重进仍保持”。证据见
`docs/phase-reports/alpha-02/ALPHA_02_SHOP_REPORT.md`。

**反思**：正确之处是把内容、事务、服务端与客户端一次打通，并用并发测试
发现真实死锁。不足之处是商品只有 4 类、没有图标与买回、价格未做经济模拟、
50 人容量未复测、开发栈尚未重启验证。

**下一步**：补跑容量与人工试玩；进入 S2，先解决职业资源可持续性（MP 回复）
与技能差异，再处理装备槽约束 TD-DATA-05。

## 2026-11-25 治理体系落地与 S2 资源可持续性

**目标**：把长期使命、自主原则、反思机制与交接规范写进项目，而不是停留在
对话；同时开始 S2，先解决“技能放几次就只能普攻”的资源断点。

**关键决策**

1. 文档分层：`PROJECT_STATUS.md` 作为唯一会话入口；`PROJECT_ROADMAP.md`
   （由 `POST_MVP_ROADMAP.md` 更名）负责路线；`EVOLUTION_LOG.md` 只记里程碑级
   判断；`WORKLOG.md` 保留任务级命令与结果。
2. 法力回复做成内容字段 + 固定 tick，服务端权威、可回放，不新增协议。
3. 对 S1 做独立代码审查，并修复审查发现的四类问题；把“横切修复要审计同类
   入口”“幂等键作用域必须一致”写入工程经验。

**结果**：文档体系与交接规范落地；战士/法师/道士 1/3/2 MP 每秒回复；单元测试
覆盖封顶、死亡、内容注入与回放；浏览器 E2E 看到 MP 下降后回满。S1 的幂等键、
数量钳制、目录容错与击杀奖励锁顺序已修复并补测试。

**反思**：正确之处是把“评审—修复—补测试”当成交付的一部分，而不是发布后再说。
不足是 50 人容量与人工试玩仍未跟上，且开发栈尚未重启，真实玩家视角证据仍缺。

## 2026-11-26 Alpha 0.2 S2-2：让职业差异可被玩出来

**目标**：在法力可回复之后，给三个职业各自 3 个可感知的技能，并为后续怪物/
死亡系统建立“状态效果”这一公共能力。

**关键决策**

1. Effect DSL 只增加 `dot` 与 `shield` 两种封闭效果，不引入任意脚本；语义与
   数值都走内容校验（ADR-028）。
2. DoT 的每跳伤害在施法时固定、不掷命中/暴击、不消耗 RNG，保证确定性回放，
   也避免“毒伤把普攻的随机数吃掉”这类难解释的问题。
3. 护盾先吸收伤害再扣 HP，通过 `shield` 事件与 `hit.absorbed` 表达，不新增
   独立 Buff 同步协议。
4. 技能栏顺序按等级/快捷键显式排序，因为 Release payload 存 jsonb 会重排键序。
5. 三套外观不与技能同批交付：先把“玩法差异”打通并验证，再单独做美术切片，
   避免一个大切片同时改领域、协议与资源管线。

**结果**：三职业 9 个技能、1/5/10 级解锁；`pnpm test` 388 个测试、25 个浏览器
E2E、4 应用构建、7 项资产不变量通过；50 人容量回归 0 资产失败。新 Release
`2026.11.26.2` 已发布并于 09:07 激活，可在 8584 试玩。E2E 发现并修复了
jsonb 键序导致的技能栏错序。

**反思**：正确之处是把确定性（DoT 不消耗 RNG）和内容校验放在实现之前，并用
真实浏览器验证；不足是外观仍未跟上，职业差异在画面上不完整；首次激活被权限
分类器拦截，说明“发布→激活”的自动化权限流程仍需在部署/运维层面明确。

**下一步**：人工试玩三职业 5 级技能；完成三套职业外观；随后进入 S3 怪物威胁
与死亡代价。

## 2026-11-26 Alpha 0.2 S2 收口：让职业差异被看见

**目标**：技能差异已经存在，但三个职业在画面上仍共用同一张占位贴图，战斗只有
缩放与浮字反馈。S2 的最后一块是让职业可辨认、动作可读，并把“动作描述”留在
内容层。

**关键决策**

1. 动画片段进角色资源 manifest（片段 → 列索引 + 帧时长 + 循环），不引入独立
   动画文件或 Phaser 全局动画注册；客户端只保留“状态 → 片段 → 帧”的纯函数
   （ADR-029）。
2. 行=方向、列=帧的贴图布局沿用阶段 3；帧名统一为 `${direction}:${frame}`，
   占位图与职业图共用，避免两套命名。
3. 服务端事件只触发表现：`attack(have skillId)` → 施法、普攻 → 攻击、`hit` →
   受击、`death`/`respawn` → 死亡/复位；伤害、命中与冷却仍由服务端裁定。
4. 占位图用零依赖脚本生成并提交，保证可复现；正式美术只替换图片与 manifest，
   不改客户端。
5. 保留 `player_placeholder` 作为未知职业回退，旧内容包不会因缺动画而崩溃。

**结果**：三职业独立贴图与 6 类动作上线；399 个单元/集成测试、30 个浏览器 E2E
通过；`classes.spec.ts` 断言职业贴图与行走/攻击/施法片段；TD-CLI-06 关闭。
随后修复了 PvP 复活后旁观者仍看到倒地的问题：死亡姿态改由权威快照 `alive`
决定，而非 `respawn` 事件清除的客户端标记（EL-020）。
资源 manifest 升到 `alpha0.2.1`，地图重新编译。E2E 发现并修复了并行用例共享
刷点造成的假失败，沉淀为 EL-019。

**反思**：正确之处是把动画时序做成纯函数并用真实浏览器验证片段切换，而不是靠
截图猜帧。不足是第一次忽略测试间的世界实体隔离，说明“测试隔离”不只是数据库；
另外正式美术仍未开始，当前只是可辨认的占位。

**下一步**：8584 目视外观与动作；进入 S3 怪物威胁与死亡代价；正式美术随 S4
统一替换。

## 2026-11-26 Alpha 0.2 S3 第一切片：让危险可以被反应

**目标**：S2 之后战斗的威胁仍只是“数值更大”。S3 要让野外真正危险，同时给
玩家一个可学习、可反应的操作空间：看到预警 → 走位 → 躲开或硬吃。

**关键决策**

1. 新增远程蜘蛛、慢速重甲守卫与精英白狼王；三类差异全部由内容参数与现有 AI
   表达，不为单个怪物增加服务端分支。
2. 精英扑击采用“提交落点 + 落地判定”：前摇开始时冻结怪物并广播 `telegraph`，
   落地 tick 才掷命中/伤害；目标离开半径即 `miss`（ADR-030）。
3. 前摇不消耗 RNG，保证确定性回放；`telegraph` 是加法事件，旧 Release 与旧
   Room 不受影响。
4. 客户端只负责表现预警圈、日志与音效，命中判定始终在服务端；开发环境暴露
   `activeTelegraphs()` 供 E2E 断言真实渲染。

**结果**：野外普通怪达到 4 种 + 1 精英，刷点 30 → 36；新增材料与掉落；内容
Release `2026.11.26.3` 发布并激活。410 个单元/集成测试、31 个浏览器 E2E 通过；
新增真实 PostgreSQL + Colyseus 集成测试证明预警先于伤害；开发栈重启后在同一
用例中复验通过。内容校验暴露了“地图刷点必须被 Release 覆盖”的部署耦合，沉淀
为 EL-021 与 TD-OPS-18。

**反思**：正确之处是把“可闪避性”放在服务端落地判定，而不是客户端预测；这样
`miss` 事件能复用既有反馈，也不引入作弊面。不足是部署顺序仍然隐性：新增刷点
与内容发布必须成对，目前只能靠启动日志发现，后续应在发布预检里拦截。另一个
不足是预警美术仍是基础图形，命中瞬间缺少冲击表现，留待 S4 美术统一处理。

**下一步**：8584 试玩新怪物与预警；随后做 S3 死亡代价（经验损失、10 级前保护、
复活点内容化），注意低等级玩家在当前经验曲线下几乎看不到惩罚，保护阈值需保持
内容可调。

## 2026-11-26 Alpha 0.2 S3 收口：让死亡有代价

**目标**：S3 第一切片让野外“可反应”，但死亡仍然免费：等待 3 秒即满状态复活，
玩家没有撤退、吃药或换图的动机。本切片给 PvE 死亡一个不摧毁进度、可内容调整
的代价，并把复活点从代码约定变成地图内容。

**关键决策**

1. 只惩罚被怪物击败：PvP 死亡维持 ADR-021 的无惩罚契约，避免野外互杀成为
   恶意惩罚工具。
2. 扣除“当前等级内经验进度”的千分比，最低为 0，等级永不下降；满级与受保护
   等级不扣。默认 10%，10 级前保护，低经验时几乎无感。
3. 规则进入内容 Release 的新可选 `rules` section；历史 payload 不补默认值，
   checksum 不变（EL-004）。运营可在内容工作台编辑并发布。
4. 扣减由 `AssetService` 在单事务内完成：先锁角色行，再写按死亡事件 ID 生成的
   幂等行；与击杀奖励共用资产队列与锁顺序（EL-012/016）。
5. 战斗结果记录统一改用带 `eventId` 的线缆事件，命令死亡与 tick 死亡只有一条
   记账路径；失败重试 3 次，最终失败计入资产失败指标。
6. 复活点在 Tiled 出生点上用 `respawn: true` 标记，编译进不可变 manifest；
   未标记的旧地图回退到第一个出生点。
7. 客户端只展示规则与服务器给出的结果：角色面板显示内容里的阈值，死亡后由私有
   系统提示告知实际损失，不做任何本地扣减。

**结果**：424 个单元/集成测试、31 个浏览器 E2E 通过；真实 PostgreSQL 集成
测试证明扣减 200 → 180、等级不变、重复 deathId 只扣一次、保护等级不扣、PvP
被击杀者经验不变。内容 `2026.11.26.4`（checksum `7f6c6914…`）发布并激活，
开发栈实测角色面板显示“-10% 经验 · 10 级前保护”。容量回归与证据见
`docs/phase-reports/alpha-02/ALPHA_02_DEATH_COST_REPORT.md`。

**反思**：正确之处是把死亡 ID 作为幂等锚点，并把命令死亡与 tick 死亡统一到
同一结果路径，避免“同一次死亡记两笔”。另一个正确判断是先截图再验收 UI，
发现规则行被角色面板裁剪后立即把它移到“经验”下方，而不是只靠文本断言。
不足是低估了新增内容 section 的横切成本（PostgreSQL 枚举迁移、运营契约联合
类型、diff 的键值假设），已沉淀 EL-022；经验仍没有连续流水，运营无法对账
（TD-DATA-11），Beta 前应补。

**下一步**：8584 试玩死亡代价与新手保护；进入 S4 装备/掉落/背包与正式美术，
同时评估经验流水与 tick p95 的容量风险。

## 2026-11-26 Alpha 0.2 S4 切片 A：让装备值得追

**目标**：S1–S3 之后战斗与死亡都有意义，但“打怪→掉落→装备→再成长”仍缺内容：
野外几乎只掉材料与皮甲，玩家没有下一件装备的目标。本切片让 1–7 级有分层装备，
让稀有掉落可感知，并让背包能比较与整理。

**关键决策**

1. 品质是可选内容字段而非独立系统：`quality?: 'common' | 'rare'`，缺省普通；
   不写默认值，历史 Release checksum 不变（EL-004）。
2. 品质只影响展示，不参与战斗计算；装备数值仍显式写在内容里，便于运营审查。
3. 新增 12 件装备，按怪物等级分配掉落，并把 3 级武器与锁子甲放进商店，让金币
   同时具备消耗端与等级目标。
4. 对比与整理放在客户端纯函数，只改变显示；服务端槽位、装备与属性快照仍权威，
   不新增协议命令。
5. 内容校验新增“非装备不得设置品质”（error）与“装备必须能获得”（warning）。
   新增 error 规则只覆盖历史数据不可能出现的情况，否则会让已发布 Release 在
   Room 启动校验时失效。

**结果**：433 个单元/集成测试、32 个浏览器 E2E 通过；新装备内容
`2026.11.26.5`（checksum `a0805598…`）发布并激活，开发栈实测商店与背包装备
展示正确。E2E 还暴露了商店面板遮挡背包按钮的问题，已改为面板互斥并登记
TD-CLI-14。

**反思**：正确之处是先用内容校验拦截“无法获得的装备”，再让客户端只做展示，
避免为了一个背包特性改协议。不足是低估了新校验规则对历史 Release 的影响：
`ContentStore` 会在 Room 启动时校验已存 payload，error 级规则等于让旧内容无法
加载；已沉淀 EL-023，后续新增语义规则先按“历史数据是否必然满足”分级。另一个

## 2026-11-26 Alpha 0.2 S4 切片 F：让 50 人的 tick 回到预算内

**目标**：S4-B 的 50 人回归 tick p95 14.75ms 高于 10ms 目标，但 p50 只有
1.1ms——问题不是平均计算量，而是长尾。本切片先证明长尾来自哪里，再只改被
证据指向的路径。

**关键决策**

1. 不用开发栈的 tsx 进程做剖面：生产构建 + 直接 `node --cpu-prof`，并用
   50 人 × 2 分钟无剖析基线做同条件对照，避免把转译、开发日志或单次波动当成
   优化效果。
2. 按 `simulateTick` 子树聚合自耗时，而不是看全进程火焰图。剖面显示 tick
   只占墙钟 2.9%，但占非空闲 CPU 39%；其中 AOI 约 61%，战斗事件序列化与
   `writev` 约 28%，寻路只有 0.4%——因此没有去“优化寻路”。
3. AOI 按 tick 去重：玩家与怪物移动先把受影响观察者入队，tick 末统一刷新。
   刷新仍在 tick 内完成，`session.visible` 对下一 tick 生效的语义不变。
4. 去掉每次刷新的中间数组/Set：`collectVisibleIds` 填充调用方 Set，
   `StateViewPublisher` 复用两个 Set；`simulateTick` 只取一次玩家列表。

**结果**：同一 2 分钟场景 p95 12.59 → 5.15ms、p99 17.30 → 7.87ms；50 人 ×
10 分钟 p95 **5.34ms**、p99 6.67ms、max 6.92ms，50/50 加入、99.0% 接受率、
784 击杀、0 资产失败、RSS 289MB。455 个单元/集成测试、38 个浏览器 E2E 通过。

**反思**：正确之处是先做“长尾 vs 稳态”的判断，再用生产构建剖面定位；如果按
路线图里“GC、寻路、AOI patch”平均用力，最可能先改错寻路。另一个正确判断是
把 AOI 批处理限制在 tick 内，不改变可见性生效边界。不足是剖面仍显示 tick 内
约 28% 花在战斗事件逐客户端 msgpackr 打包与 `writev`，团战事件量增长前需要
单独设计批量协议；资产队列 p95 48ms 也没有变化，只是不阻塞 tick。全量 E2E
首轮仍有一次已知的 250ms 时序抖动，说明测试环境本身仍是噪声源。

**下一步**：8584 试玩并观察手感；S4 只剩正式美术（TD-CLI-13）；后续容量
回归继续记录 p95/p99 趋势，团战或经济压力出现时再处理 TD-SRV-10/TD-SRV-03。

**关键决策**

1. 队伍是 Room 内的临时社交状态，放内存而不是数据库；传送、最终离开或宽限
   结束都会移除队员，进程崩溃丢队伍是可接受损失（ADR-035）。这避免了为
   “临时关系”新增表、迁移和清理任务。
2. 名单只走私有 `party.snapshot`，不进入公开 Room State：同图陌生人无法读取
   他人的等级、HP 与在线状态（延续“私有数据不得进入公开状态”）。
3. 共享经验是独立、确定性的幂等事务：击杀者保留完整掷骰奖励；队友按内容
   基础经验的固定千分比获得分享，不消耗 RNG、不发金币、不掷掉落、不推进
   任务。若让队友“再领一次击杀奖励”，会重复掉落与金币，无法解释也无法对账。
4. 邀请规则全部服务端裁定：同 Room、15 格内、同目标只留一条邀请、30 秒过期、
   内容配置队伍上限；伪造的接受请求不能取消别人的邀请。
5. 队伍命令复用 `CommandGuard`（协议/重复 id/序号/限频），但同步执行，不占用
   资产队列。

**结果**：契约、内容规则、`PartyRegistry`、服务端命令、共享经验事务与客户端
面板全部交付；490 个单元/集成测试、40 个浏览器 E2E 通过；内容 `2026.11.27.1`
发布并激活；开发栈 84–87 用真实 Chromium 跑通双人组队/离队/传送断队；50 人
× 2 分钟 p95 5.09ms、10 分钟正式回归 p95 6.19ms、741 击杀、0 资产失败；
资产不变量 7/7 为 0。同日补充：归属窗口内同队成员可拾取击杀掉落（物品仍只有
一个实例、先到先得），修复“队友捡不到、路人反而能捡”的不合理体验。

**反思**：正确之处是把“分享”做成确定性事务而不是第二次抽奖，也把队伍状态
留在它真正归属的 Room 内。不足是“1 人队伍”没有自动解散，UI 也还不能移交
队长或邀请不在视野内的玩家；跨图组队与队伍聊天仍缺失。E2E 上再次证明：
“同图”不等于“同房间”，`?fresh=1` 会创建隔离房间（EL-030）。

**下一步**：8584 双人试玩并观察经验分享是否符合预期；根据反馈决定先做队伍
聊天/移交，还是继续任务系统深化；正式回归观察 4 人满队的经验膨胀。

## 2026-11-27 Alpha 0.3 S3-A：把“每天回来”做成可重置的确定性状态

**目标**：一次性任务链完成后，玩家缺少每天上线的理由。本切片交付内容驱动的
每日任务：区服定义重置时刻，玩家每天可重新接取与交付；进度和奖励仍走既有
事务，不新增发奖链路。

**关键决策**

1. 不做“交付即删除/重置任务行”，而在 `character_quests` 上增加周期键，唯一
   约束扩为 `(角色, 任务, 周期)`：历史保留、同周期防重复、跨周期自然重开。
2. “一天”由内容 `rules.dailyReset` 描述，周期键是注入时钟的纯函数；客户端
   只收到权威的 `nextResetAt`，按玩家本地时区显示，不参与判定。
3. 旧周期的日常记录在视图与击杀推进中视为不存在；一次性任务与旧 Release
   完全不变。
4. 在线玩家跨日时由 Room 每 30 秒检测一次并重发任务快照，快照由内存记录
   计算，不引入数据库轮询或定时任务。

**结果**：契约、内容、领域、应用、迁移 0009、服务端与客户端全部交付；
530 个单元/集成测试、43 个浏览器 E2E 通过；内容 `2026.11.27.3` 发布并激活；
真实 Chromium 在宿主机 8584 看到日常标签、重置时刻与接取后的追踪器；
50 人 × 2 分钟 tick p95 5.11ms、p99 6.14ms、0 资产失败；资产不变量 7/7 为 0。

**反思**：正确之处是把“重置”做成时间与内容的纯函数，而不是清理任务或可变
状态；周期键让历史、唯一性与重开同时成立，且不需要修改交付事务的幂等模型。
不足是日常仍只有击杀目标、主线仍只有 3 步；在线重置有最多 30 秒延迟且没有
倒计时；每日历史行暂时没有清理策略（TD-DATA-12）。跨 section 的新约束再次
提醒：修改内容校验前要先检查“旧 Release 夹具”是否会因此失效（EL-037）。

**下一步**：8584 试玩日常与跨日重接；S3-B 优先 10 步主线任务链；副本实例
先写 ADR；确认远端 CI 与正式美术。

## 2026-11-27 Alpha 0.3 S3-B：把“找路、打架、回城”变成一次点击

**目标**：每日任务和主线已经给出目标，但新玩家仍要自己找路、逐只点怪、走回

5. 自动战斗 E2E 会抢占共享野区，新增仅开发环境的 `?freshTransfer=1`，让场景

**结果**：契约、纯路由、Room 导航、客户端按钮/横幅/提示与真实 E2E 全部交付；

无数据库迁移。真实截图暴露并修复了野外任务显示 `town_guard` 的问题。

**反思**：正确之处是把“自动化”限制为服务端意图与既有战斗/交付链路，玩家
随时可以接管；也把路线计算抽成纯函数，能用固定地图做确定性测试。不足是自动
战斗只会普攻、目标选择可能抢怪、意图在关闭页面后丢失，且全量 E2E 在 2 worker
软件渲染下仍会出现时序/共享实体抖动（单跑与串行均通过）。Room 编排继续增长，

## 2026-11-27 Alpha 0.3 S3-E：让战利品归属与拾取都变得不像“操作系统”

**目标**：战斗已经自动攻击与一键任务，拾取却仍要逐件点击；战利品按最后一击
归谁，组队补刀与路人抢刀都不公平；远处点击只提示距离过远。本切片把拾取变成
“归属者的东西自己飞进背包”，并给首领与未来活动提供无归属、锁定 60 秒的争夺
掉落。

**关键决策**

1. 归属从“最后一击”改为“首次接战 + 持续伤害刷新”。最后一击决定奖励会鼓励
   抢刀；按伤害排序又对拉怪、治疗和换人不友好。首次接战简单、可解释，且归属
   超时/离开/重生都有明确释放条件。
2. 自动拾取复用既有拾取事务，而不是在 Room 里直接移动物品。自动化越方便，
   越不能绕开行锁、幂等键与背包校验；失败（背包已满）退避并提示，而不是每次
   tick 重试。
3. 归属者自动拾取优先于队伍手动共享：用户明确“飞给归属者，不是击杀者”。队伍
   共享保留为归属者不在自动范围时的兜底，并在 ADR-035 中修订说明，避免两套
   规则互相矛盾。
4. 争夺掉落是内容标记而不是新系统：`lootEntry.contested` + `rules.loot`，
   无归属、锁定、手动拾取，世界首领的专属掉落先落地；未来活动可直接复用。
5. 远处拾取不新增协议：客户端用既有 `move.to` 走近，再发既有 `loot.pickup`；
   锁定掉落不走近，只显示倒计时。少一条协议就少一套幂等与作弊面。
6. 自动化改变了测试形态：旧用例假设玩家会手动点掉落，现在要断言“无需点击
   即入包”；需要验证手动共享兜底时显式关闭自动拾取，而不是和 200ms 的 tick
   抢时序。

**结果**：怪物归属、自动拾取与飞行动效、争夺掉落与锁定倒计时、远处自动走近
全部交付；576 个单元/集成测试、47/47 全量 E2E 通过；50 人 × 2 分钟 tick p95
3.4ms、0 资产失败；资产不变量 7/7 为 0；内容 `2026.11.27.6` 已激活；迁移
`0010` 增加掉落锁定列；8584 实测自动拾取与背包脉冲。

**反思**：正确之处是把归属做成领域状态、把自动拾取压在既有事务上，并让争夺
掉落完全走内容；失败与所有权都在服务端裁定。不足是归属仍只在进程内、玩家看
不到归属标识；攻击不锁定，其他人仍可打你的怪（只是拿不到奖励）；远处走近
没有浏览器 E2E，且没有“走到后等待解锁”的争夺掉落交互。

**下一步**：组队试玩首领争夺掉落与远处走近；补归属可见标识与自动走近 E2E；
S3-D2 到达类目标或社交深化；副本实例先写 ADR。

## 2026-11-27 Alpha 0.3 S3-D2：让地图坐标成为任务目标

**目标**：任务此前只有击杀与收集，地图只是战斗背景。本切片增加“到达地点”
目标，让探索本身成为可交付的目标，并给一键导航一个不依赖怪物的用途。

**关键决策**

1. 完成判定只读服务端模拟位置，客户端不提交“我已到达”。位置是服务端权威
   的核心资产，任何位置类目标都不能接受客户端自报。
2. 到达是“曾经发生过的里程碑”，不是“当前可派生的事实”。收集任务可以从背包
   实时派生，到达必须在第一次命中时落状态；否则离开区域就会回退。状态写入
   用角色行锁 + “只更新 active 行”的条件保证幂等。
3. 观测放在 tick 的纯内存扫描里，写入放到既有资产队列。tick 不等待 SQL，
   也不需要为位置判定新增数据库读取或协议。
4. 一键导航复用 `hunt` 目的而不是新增协议：到达与狩猎共享“前往目标”的语义，
   差别只在目标选择和是否进入自动攻击。少一条协议就少一套幂等与作弊面。
5. 内容校验必须验证目标格可行走且在范围内。否则一条内容配置就能发布一个
   永远无法完成的任务；可达性留给运行时导航报错。

**结果**：到达目标、两条任务、服务端位置裁定、每日周期隔离与一键探索全部
交付；587 个单元/集成测试、48/48 全量 E2E 通过；50 人 × 2 分钟 tick p95 3.35ms、
0 资产失败；资产不变量 7/7 为 0；内容 `2026.11.27.7` 已激活；无数据库迁移；
8584 实测接取→自动探索→交付，金币 50 → 55。

**反思**：正确之处是把“位置”留在服务端、把“到达”写成一次受限状态迁移，并
让导航复用既有目的与资产队列；内容校验也把不可完成的配置挡在发布前。不足是
世界内没有目标标记，手动完成时只能按坐标找（TD-CLI-24）；每日东境巡逻的路程
较长且穿越开放 PvP，自动导航只走路不战斗，试玩后可能需要调整距离或等级；
到达目标目前是单人进度，没有组队共享。

**下一步**：8584 试玩每日东境巡逻与跨图自动导航；下一片优先队伍社交（聊天/
移交/踢人，TD-CLI-17），副本实例先写 ADR；补世界内到达目标标记。

## 2026-11-27 Alpha 0.3 S3-M：把移动从“格”做成“方向”

**目标**：四方向网格移动让斜向目标走 L 线，键盘也只有点击一种操作。本切片把
移动扩展为八方向，并补上 WASD/方向键与空格停止，同时保持服务端权威与客户端
预测的一致性。

**关键决策**

1. 八方向不是给 BFS 加四个邻居就结束：斜向必须要求两个正交邻格可走，否则
   角色会切过墙角；对角步必须按 √2 距离计时，否则斜向会快 41%。阻挡、速度、
   预测三处必须一起改。
2. 移动是服务端权威 + 客户端预测的双实现。寻路、模拟步进、注入路径校验、
   怪物移动、客户端路点与端到端测试共享同一条规则；只改一处会在真实浏览器里
   表现为抖动或穿墙。
3. 朝向枚举追加值而不是重排：保留 0–3，对角 4–7；旧持久化与旧客户端无需迁移，
   四方向贴图在表现层映射。
4. 停止需要显式协议。客户端预测通常领先服务端，用客户端坐标发 `move.to` 会多走
   一段；`move.stop` 复用统一命令门禁，清路径、停自动攻击并返回空 ack。
5. 为了验证“逐帧预测而非快照跟随”，先让测试的判据独立于软件渲染帧率：
   统计“服务端位置未变、预测位置已前进”的采样，而不是比较采样数或 FPS。

**结果**：八方向寻路/阻挡/速度/朝向/预测、键盘短步与空格停止全部交付；
600 个单元/集成测试与 49/49 串行浏览器 E2E 通过；50 人 × 2 分钟 tick p95
3.72ms、0 资产失败；8584 实测 D+S 两轴移动、空格后权威位置不变；关闭
TD-CLI-07/TD-CLI-18；无数据库迁移、无内容发布。

**反思**：正确之处是把移动当成一套跨端规则而不是一次寻路改动，并用 ADR 记录
斜向阻挡与速度；测试失败也不是简单放宽断言，而是先找出两个真实前提错误
（巡游怪越过 AOI、20Hz patch 下帧率无法区分预测）。不足是正式美术仍只有
四方向帧，斜向表现是映射；狭窄走廊拐角仍需一个正交步，这是有意碰撞规则；
2-worker 软件渲染全量仍不适合作为平滑度证据。

**下一步**：队伍社交（聊天/移交/踢人，TD-CLI-17），副本实例先写 ADR；
补世界内到达目标标记；正式美术与八方向角色帧。

## 2026-11-27 Alpha 0.3 S4-A：把队伍从“名单”做成“可协调的小队”

**目标**：S1 的组队解决了“在一起打”，但队伍只有名单与离队，无法指定指挥、
无法移除捣乱成员、无法单独沟通。本切片补齐队伍聊天、队长移交与踢人，让组队
成为可以自我管理的社交单元。

**关键决策**

1. 权限放进 `PartyRegistry`，而不是 Room 或 UI。Room 只解析命令、走既有门禁并
   路由；隐藏按钮不算权限，注册表统一返回可区分的拒绝原因。
2. 踢人不是断线。被踢者保留世界会话与 presence，只失去队伍归属；其所在 Room

3. 队伍聊天复用地图聊天的治理链，而不是新增一套协议：同一个 `chat.send`，

   按成员所在 Room 端口投递，永不进入公开状态。
4. 兼容优先：省略 `channel` 默认地图聊天，旧客户端行为不变；无协议版本升级、
   无内容发布、无数据库迁移。

测试覆盖队伍消息隐私、跨图投递、权限拒绝与名单清理；开发栈已重启到本切片。

**反思**：正确之处是把社交权限与投递放在进程级服务、把聊天治理留在唯一一条链
上；测试也优先验证“陌生人收不到”和“跨图队友收得到”这两个真正决定设计成败的
性质。不足是被踢者只能从面板消失推断，没有定向提示；队伍聊天没有离线队列；
按名字邀请仍缺失，临时队伍只能依赖附近列表。队伍状态仍是单进程（TD-SRV-11），
跨进程前需要共享协调。

**下一步**：世界内到达目标标记（TD-CLI-24）；按名字邀请与队伍标记（TD-CLI-17
剩余）；3 人副本先写 ADR；正式美术与八方向角色帧。

## 2026-11-28 Alpha 0.3 S4-B：好友关系是持久的，在线状态是实时的

**目标**：队伍解决了“在一起打”，但没有好友关系，离开视野就无法再组队，也没有
办法跨图找到熟人。本切片交付好友申请/列表/在线状态与好友跨图组队，并并让聊天变成标准布局：日志默认显示全部频道，
标题栏只筛选，输入行左侧选择发言频道。用户已确认的顺序是：频道筛选 + 好友 → 私聊 → 行会。

**关键决策**

1. 好友关系必须持久化，在线状态必须实时。关系落 PostgreSQL（无序对唯一），
   在线状态复用进程级 presence；快照把两者合并，旧关系不会伪造“在线”。
2. 无序对 + 条件更新让社交命令天然幂等：重复申请返回同一行，重复接受返回同一
   关系，双方互相申请直接成为好友；拒绝删除申请，删除好友删除关系。
3. 好友只放宽“距离”，不放宽队伍语义。跨图/超范围邀请要求已接受好友且目标
   在线，创建、接受、共享奖励与跨图保留仍走 ADR-035/036 的既有路径。
4. 筛选与发言分离：日志默认全部、标题栏只筛选、输入行选择发言频道，且都属于
   客户端展示层。服务器继续只投递有权限的消息，客户端选择不能
   成为隐私边界。
5. 共享事实必须有唯一所有者。实现时发现未组队玩家离开世界后 presence 从未
   清理，导致好友“幽灵在线”和跨图邀请落空；修复为最终离开无条件清理，
   过图只标记离线，并把提取独立在线目录登记为 TD-SRV-14。

**结果**：好友申请/接受/拒绝/删除、持久化关系（迁移 0011）、在线状态与上下线
事件、好友跨图组队邀请、好友面板与聊天标准布局全部交付；623 个单元/集成测试与
51/51 全量浏览器 E2E 通过；真实 PostgreSQL 覆盖关系事务，真实 Room 覆盖跨图
邀请与陌生人拒绝；开发栈已迁移并重启。

**反思**：正确之处是把“关系”和“状态”分开：关系可恢复，状态只描述当下；
幂等收敛避免了为社交命令引入一整套资产级事务；好友规则只放宽距离，控制了
影响面。不足是好友申请只有命令限频，没有每日上限与黑名单；没有离线消息；
按名字搜索仍缺失；在线状态还寄居在 PartyService，私聊与公会之前应提取为
独立在线目录（TD-SRV-14）。

**下一步**：私聊（好友/最近同玩入口、跨图投递、隐私与限频）；行会先写 ADR；
世界内到达目标标记与按名字邀请作为小切片穿插。

## 2026-11-28 Alpha 0.3 S5-A：行会是第一种“持久归属”，不是更大的队伍

**目标**：把一次性组队关系变成稳定的多人身份。行会需要跨重启、过图与重新
登录保留归属，同时继续提供在线名单与成员频道；这正好处在队伍（进程内）与
好友（持久关系）之间，必须先明确数据归属。

**关键决策**

1. 行会与成员写入 PostgreSQL，职位与生命周期在行锁事务内变更；在线、等级、
   职业与存活状态不落库，生成快照时从 `PlayerDirectory` 合并。这样“归属是
   事实、在线是瞬时状态”，重启后名单仍在而在线状态自然重建。
2. 不把行会塞进公开 Room State；名单、邀请、在线变化与聊天都走私有无状态

3. 最小职责模型：只有会长可邀请/踢人/解散；会长离会时自动交给最早加入的

   有真实需求时再做。
4. 邀请复用队伍邀请的形态：进程级、30 秒 TTL、每目标一条、经目录跨图投递，
   过图后重发；接受时再锁行会行复核人数与归属，邀请本身不被当作加入许可。
5. 行会聊天只增加一个频道值，复用既有过滤、限频、禁言与去重；消息不落库、
   不进入公开状态。成员查询走数据库，30 人上限下可接受，缓存留作指标触发。

**结果**：创建、跨图邀请、接受/拒绝、名单与在线状态、离会/踢人/解散与行会
频道全部交付；迁移 `0012`；650 个单元/集成测试、52/52 浏览器 E2E、构建、
50 人 × 2 分钟容量 sanity（p95 3.64ms、0 资产失败）与资产不变量 7/7 通过；
无内容发布、协议版本不变。8584 双浏览器实测创建→邀请→接受→行会聊天通过。

**反思**：正确之处是把“持久归属”与“在线状态”拆开，并让 Room 只做门禁、
presence 合并与路由；权限集中在应用服务事务里，并发超员与双会长由行锁和
部分唯一索引兜底。不足是最小职责模型只有会长一个权限角色，申请、公告与
经济都还没有；行会聊天每条消息查询成员表，邀请仍是进程内状态。这些不是
“以后再说”的借口，而是明确记录在多进程与经济切片前的触发条件。

**下一步**：玩家交易最小版先写 ADR；再评估 3 人副本实例或排行榜；行会申请/
公告/经济按试玩反馈推进，正式美术与远端 CI 持续开放。

## 2026-11-28 Alpha 0.3 S5-B：可发现的行会与可等待的申请

**目标**：试玩反馈指出行会入口只对“被邀请的人”有意义。本切片让未入会玩家
看到本区服的行会并主动申请，同时不把成员名单、在线状态与申请内容变成公开
信息。

**关键决策**

1. 目录与名单分离：目录只返回行会名、会长名、人数/上限与“我是否申请过”；
   成员名单与申请列表继续只走私有快照。公开的是“行会存在”，不是“谁在里
   面”。
2. 申请持久化到 PostgreSQL，而不是像邀请一样放进程内：会长离线时提交的申请
   必须在其上线后仍在。一个角色可申请多个行会，接受其中一个时清理其余。
3. 审批只有会长；接受申请与“加入成员 + 清理申请”在同一事务，并锁行会行
   复核人数与归属。申请人已加入其他行会时，过期申请也要删除——用“事务提交
   标记后再报错”避免删除被回滚。
4. 申请到达只通知会长并刷新其私有快照，不广播给全体成员；拒绝只通知申请人。
   通知是提示，事实以持久化状态与下一次快照为准。
5. 目录查询在 tick 之外，按人数/创建时间排序并限制 50 条；申请列表限制
   100 条。规模触发条件（分页/搜索/过期）写入 TD-SRV-18，而不是提前加。

**结果**：目录、申请、审批、拒绝与状态回显全部交付；迁移 `0013`；659 个单元/
集成测试、52/52 浏览器 E2E、构建、50 人 × 2 分钟容量（50/50、p95 3.8ms、
0 资产失败）与资产不变量通过；8584 双浏览器实测目录→申请→接受通过。

**反思**：正确之处是把“发现”和“关系”分成公开摘要与私有事实，申请审批复用
行会事务与行锁，而不是另建一套加入路径。不足是申请无过期、目录无分页/
搜索，压测脚本也因为机器人走进传送门暴露了“测试工具也需要边界验证”的问题。
两者都被修正或记录，而不是用放宽断言掩盖。

**下一步**：玩家交易最小版先写 ADR；再评估 3 人副本或排行榜；行会公告/职位/
搜索按试玩反馈推进，正式美术与远端 CI 持续开放。

## 2026-11-28 Alpha 0.3 S5-C：交易把“资产”从单角色推进到双角色

**目标**：让玩家之间能直接交换装备、材料与金币。此前所有资产命令都以一个
角色为中心，交易是第一个必须在同一事务里同时改变两个角色、两个背包和两个
钱包的用例。

**关键决策**

1. 交易会话留在 Room 内存，结算才进入 PostgreSQL。交易是短生命周期的交互
   状态，持久化会话会引入恢复语义与过期清理；已提交的资产交换不受重启影响。
2. 结算按角色 UUID 升序锁两个角色行，与拾取/商店/装备共用同一把串行锁；
   A↔B 与 B↔A 交叉交易不会死锁。幂等键是 `tradeId`，不是某一次锁定的
   commandId。
3. 槽位交换先把移动物品停放到接收方的唯一负槽位，再删除/合并被消耗的堆叠，
   最后写正式槽位；避免唯一索引冲突，同时保留物品实例 ID 与掉落审计引用。
4. 报价只是意图：数量、可交易性、钱包余额与物品归属全部在结算事务内重新
   读取；失败整体回滚并让交易回到可编辑状态。
5. 绑定规则复用商店语义（无出售价的新手武器不可交易），客户端隐藏、服务端
   拒绝；交易状态只走私有消息，公开 Room State 不新增字段。
6. 面对面约束：同图、3 格内、双方存活；离开/过图/断线/死亡立即取消，不让
   “远程交易”或“离线成交”成为绕过风险与距离的入口。

**结果**：邀请/接受/拒绝、双报价、双锁定、原子结算、金币账本、取消与生命
周期全部交付；683 个单元/集成测试、全量 54/54 浏览器 E2E、构建、50 人 ×
2 分钟容量（p95 3.61ms、0 资产失败）与资产不变量 7/7 通过；无迁移、无内容
发布、协议版本不变。8584 已重启到本切片代码。

**反思**：正确之处是把“交易状态”和“资产结算”分开，并让结算复用角色行锁
而不是新建一套并发模型；槽位停车是在测试暴露真实索引约束后补上的，而不是
假设“交换不会撞槽位”。不足是只支持整堆交易，没有税率、交易历史、部分数量
与黑名单；交易会话仍是 Room 内存状态（TD-SRV-19），金币在玩家间零损耗
流动（TD-ECO-06）。这些限制已写入债务，等真实交易量与试玩反馈决定优先级。

**下一步**：按试玩反馈在 3 人副本实例、排行榜最小版与行会/交易迭代之间
选择；默认优先多人价值更高、但需要动态实例 ADR 的 3 人副本。
